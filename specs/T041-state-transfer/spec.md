## 1. Overview

Девятая задача эпика E1 (карточка T009, `deps: T034`). Оперативный слой
состояния (`$DT_STORE`) **сознательно не ездит с git** (§233): не приезжает с
`git clone`, не уходит на `push`, не синхронизируется между машинами. Это цена
за отсутствие merge-конфликтов состояния — но состояние всё же нужно уметь
переносить между машинами Разработчика вручную. `dt state export/import` —
явный канал этого переноса.

Переносятся **только записи задач и счётчик** (§209): реестр сессий
(`sessions/`) и привязки по worktree (`by-worktree/`) описывают конкретную
машину — `session_id` и пути чужой машины там бесполезны (нет соответствующего
транскрипта/worktree). Импорт с явной политикой разрешения конфликтов ID;
счётчик после импорта поднимается так, чтобы будущие ID не переиспользовались.

## 2. Сценарии использования

- **Переезд на другую машину.** Разработчик поднимает рабочее окружение на
  втором ноутбуке: `dt state export state.json` на первом, перенос файла,
  `dt state import state.json` на втором — записи задач и счётчик на месте,
  можно продолжать (сессии/привязки — локальные, наберутся заново).
- **Прямой канал между машинами (если развилка B — да).**
  `dt state export - | ssh other 'cd repo && dt state import -'` — перенос без
  промежуточного файла, ровно под сценарий «между машинами».
- **Слияние состояний с конфликтом.** На обеих машинах успели завести задачи
  под пересекающимися ID. `dt state import` без флага прерывается со списком
  конфликтующих ID; Разработчик выбирает `--on-conflict skip` (оставить
  локальные) или `overwrite` (взять импортируемые).
- **Первый потребитель — сам dreamteam (позже).** После `dt migrate tasks`
  (T042) состояние можно будет гонять между машинами; T041 — механизм.

## 3. Functional Requirements

### `dt state export <file>`

- ДОЛЖНА: собрать в переносимый файл **только** записи задач
  (`$DT_STORE/tasks/T<NNN>.md`) и значение счётчика (`$DT_STORE/counter`).
- ДОЛЖНА: НЕ включать `sessions/` и `by-worktree/` (машинно-специфичны, §209).
- ДОЛЖНА: сохранять запись целиком, включая unknown-поля frontmatter и тело
  (`## Handover` и пр.) — round-trip модели T033.
- ДОЛЖНА: экспортировать по **каноническому** ID (имя файла = `id`, как
  `load_all_tasks`).
- ДОЛЖНА (развилка B — да): писать в stdout при `file == '-'`.
- ДОЛЖНА: перезаписывать существующий выходной файл (это явный вывод).

### `dt state import <file> [--on-conflict skip|overwrite]`

- ДОЛЖНА: прочитать файл переноса, восстановить записи задач и импортируемый
  счётчик.
- ДОЛЖНА: **конфликт** = ID есть и в импорте, и в локальном store. Без
  `--on-conflict` → прерывание exit 1 со **списком всех** конфликтующих ID,
  **ни одной** записи не записано (pre-check до записи).
- ДОЛЖНА: `--on-conflict skip` — конфликтные ID пропустить (оставить
  локальные), неконфликтные импортировать. `--on-conflict overwrite` —
  конфликтные перезаписать импортируемыми, неконфликтные импортировать.
- ДОЛЖНА: после импорта поднять счётчик до `max(локальный, импортируемый
  счётчик, наибольший импортируемый ID-номер)` — гарантия, что `allocate_id`
  (T034) впредь не переиспользует номер (§211).
- ДОЛЖНА: валидировать каждый импортируемый ID против `T[0-9]{3,}` **до**
  обращения к файловой системе (защита от path traversal из подделанного
  файла).
- ДОЛЖНА: на битом/неполном файле переноса (не JSON, нет обязательных полей,
  неверные типы) — внятная ошибка exit 1, без записи.
- ДОЛЖНА (развилка B — да): читать из stdin при `file == '-'`.

### Общее

- ДОЛЖНА: неинтерактивность; `TaskError`/`DtHomeError`/`OSError` → stderr +
  exit 1 без traceback (образец `_run` из `task_cli`).
- ДОЛЖНА: чистое ядро (сбор/сериализация/парсинг/слияние) — **typer-free И
  git-free**; git не участвует вовсе (store резолвится через `paths`, но сами
  export/import — чистые операции над store). Повторяет расслоение T035/T037.
- НЕ ДОЛЖНА: валидировать граф задач при импорте (циклы/висячие ссылки) — это
  `dt task check` (T035), запускается отдельно. Импорт механический.

## 4. Success Criteria

- `export` → `import` на другой (пустой) store: множество записей и счётчик
  идентичны исходным; тела и unknown-поля сохранены побайтово (round-trip).
- `sessions/` и `by-worktree/` в файле переноса отсутствуют; их наличие в
  исходном store не влияет на результат.
- `import` с пересечением ID без флага: exit 1, перечислены **все** конфликты,
  локальный store не изменён.
- `--on-conflict skip`: конфликтные записи не тронуты, неконфликтные добавлены.
  `overwrite`: конфликтные заменены, неконфликтные добавлены.
- После импорта `dt task new` выдаёт ID строго больше любого локального и
  импортированного (счётчик поднят).
- Подделанный ID (`../..`, абсолютный путь) в файле → отказ, записи вне
  `tasks/` не появляются.
- 4 гейта зелёные; coverage ≥ 80% на новом коде.

## 5. Key Entities

- **state bundle** — переносимая единица: `{version, counter, tasks[]}`.
  `tasks[]` — полные записи (frontmatter + body). Формат сериализации —
  развилка A.
- **counter** — high-water-mark номеров ID (T034). Экспортируется как есть;
  при импорте берётся `max`, никогда не откатывается.
- **conflict** — ID, присутствующий и в импорте, и локально. Разрешается
  политикой `--on-conflict` (default — прерывание).
- **ImportResult** — результат слияния: списки `imported`/`skipped`/
  `overwritten` и новый счётчик (для отчёта человеку/`--json`).

## 6. Assumptions & Constraints

- Store резолвится из git-common-dir (T033); export/import работают над
  `$DT_STORE` текущего репозитория. Вне git без `DT_HOME` — внятная ошибка.
- Перенос — **ручной** канал между машинами Разработчика; частота низкая,
  атомарность транзакции не требуется (best-effort последовательная запись
  после pre-check конфликтов). Файл переноса Разработчик перемещает сам.
- Импорт доверяет содержимому лишь настолько, чтобы не дать себе выстрелить в
  ногу (валидация ID, формат) — это не граница безопасности против враждебного
  ввода, а защита от порчи/опечатки (как `DT_HOME`-override в T033).
- `session_id`/пути worktree чужой машины бесполезны локально — потому и не
  переносятся (§209), а не по соображениям приватности.

## 7. Out of Scope

- `dt migrate tasks` (парсинг BOARD/BACKLOG, `.bak`, удаление BOARD.md) — T042.
- Перенос `sessions/` и `by-worktree/` — сознательно исключён (§209).
- Автоматическая синхронизация/облако/git-транспорт состояния — вне слоя
  (§233): канал ручной и явный.
- Валидация графа при импорте (циклы, висячие `deps`/`parent`) — `dt task
  check` (T035) отдельной командой.
- Шифрование/подпись файла переноса, дельта-синхронизация, слияние **тел**
  задач при конфликте (только whole-record skip/overwrite).

## Clarify (2 развилки согласованы опросником 2026-08-01)

### Resolved

- **A. Формат файла** → «JSON одним файлом». Самодостаточный
  `{dt_state_version, counter, tasks:[...]}`; каждая запись — `model_dump` +
  `body` (unknown-поля сохраняются через `extra='allow'`). Согласуется с
  `--json` везде в коде, лёгкая детекция конфликтов, human-readable diff, без
  бинарщины. Отвергнут tar.gz (непрозрачный, сложнее тестировать/читать).
- **B. Поддержка `-`** → «Да». `dt state export -` → stdout, `dt state import
  -` → stdin. Прямой канал `dt state export - | ssh other 'dt state import -'`
  ровно под сценарий «между машинами», дёшево при JSON. Обычный путь-аргумент
  тоже поддержан.

## Analyze (Claude)

- 🟢 **A1. Расслоение.** Чистое ядро `dt/state.py` (typer-free И git-free):
  `export_bundle(store) → Bundle`, `serialize`/`parse` (JSON),
  `import_bundle(store, bundle, on_conflict) → ImportResult`. Обёртка
  `state_cli.py` резолвит store (`ensure_store`/`store_dir`), делает I/O файла/
  stdio. git не участвует вообще. Повторяет T035/T037.
- 🟡 **A2. Мелкий публичный API в `tasks.py`.** Ядру нужны примитивы store,
  сейчас приватные: чтение/подъём счётчика и валидированный путь записи.
  Ввожу тонкие публичные обёртки `read_counter`, `advance_counter`
  (`max`-семантика уже в `_write_counter`), `record_path` (валидирует ID через
  `_ensure_valid_id` → защита от traversal). Делегируют в существующие
  приватные; переиспользуются в T042 (migrate). Не дублирую layout store.
- 🟢 **A3. Round-trip записи.** Экспорт: `data = task.model_dump(mode='json');
  data['body']=task.body` (как `_task_obj` в `task_cli`). Импорт: `body =
  data.pop('body',''); Task(**data, body=body)` — pydantic коэрсит ISO-даты
  обратно в `date`, `extra='allow'` возвращает unknown-поля. `save_task`
  пишет. Побайтовая идентичность тела/полей.
- 🟢 **A4. Pre-check конфликтов.** Сначала считаю `conflicts = bundle_ids ∩
  local_ids`. Default (флага нет) и есть конфликты → `TaskError` со
  **отсортированным** списком, **до** любой записи (success-критерий «ни одной
  записи»). `skip`/`overwrite` — план, затем запись. Порядок гарантирует
  «всё-или-ничего» на этапе решения.
- 🟢 **A5. Счётчик после импорта.** `advance_counter(store, high)`,
  `high = max(bundle.counter, max(id_num импортируемых, 0))`. `advance_counter`
  уже берёт `max` с локальным → итог = `max(локальный, bundle.counter,
  наибольший импортируемый номер)` (§211). Поднимаю **всегда** (даже при
  skip-only): другая машина могла выделить выше.
- 🟢 **A6. Path traversal.** Каждый импортируемый ID валидируется
  `record_path` (→ `_ensure_valid_id`, `T[0-9]{3,}`) **до** записи; подделка
  `../..`/абсолютный путь → `TaskError`, файлов вне `tasks/` не появляется
  (та же защита, что T034/T036 A7).
- 🟢 **A7. Битый bundle.** `parse`: `json.loads` → `TaskError` на
  `JSONDecodeError`; проверка обязательных ключей и типов (`counter` int,
  `tasks` list of dict); реконструкция `Task(**data)` → pydantic
  `ValidationError` мапится в `TaskError`. Ошибка до записи.
- 🟢 **A8. stdio (`-`).** `export`: `-` → `typer.echo`/stdout, иначе
  `path.write_text`. `import`: `-` → `sys.stdin.read()`, иначе
  `path.read_text`. Единственная ветка I/O в обёртке; ядро всегда над строкой.
- 🟢 **A9. Исключение sessions/by-worktree.** Экспорт читает только
  `load_all_tasks` + счётчик — `sessions/`/`by-worktree/` не читаются вовсе,
  исключены по построению (§209), не нужно спец-фильтра.
- 🟢 **A10. `import` — keyword.** Имя команды `'import'` задаётся строкой в
  декораторе (`@state_app.command('import')`), функция — `_import` (как `_new`
  и пр. в `task_cli`). Проблемы нет.
