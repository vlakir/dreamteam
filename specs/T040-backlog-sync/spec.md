## 1. Overview

Восьмая задача эпика E1 (карточка T008, `deps: T034`). Под новым слоем
состояния источник истины о задачах — оперативный store (`$DT_STORE/tasks`),
а `BACKLOG.md` перестаёт быть местом ручного ведения и становится
**проекцией store в долговременный git-слой**: «что мы собираемся делать».
`dt backlog sync` перестраивает этот файл из записей задач.

Смысл разделения (design §215): git хранит намерение (какие задачи открыты,
их зависимости, ссылки на спеки), оперативный слой — их текущее положение
(`todo`/`doing`/`review`). Поэтому содержимое BACKLOG.md **статус-независимо**:
переход `todo → doing → review` не меняет в файле ни байта — меняет только
заведение, завершение, переименование или переосмысление задачи. Это убирает
главный источник merge-конфликтов: две ветки больше не редактируют один
markdown-канбан.

## 2. Сценарии использования

- **Планирование на основной ветке.** Человек/агент завёл несколько задач
  через `dt task new`, часть закрыл. `dt backlog sync` на `main`
  пересобирает BACKLOG.md — незавершённые задачи в стабильном порядке,
  один коммит, никаких ручных правок markdown.
- **Возврат на main после merge PR.** Задача уехала в `done`, её запись в
  store обновилась. На основной ветке `dt backlog sync` убирает её из
  BACKLOG.md (долговременный след завершённого — в CHANGELOG, не здесь).
- **Отказ на ветке задачи.** Агент по ошибке зовёт `sync` на `T041-...`.
  Команда отказывается (не основная ветка) с подсказкой про `--force` —
  иначе две ветки с новыми задачами дают ровно тот merge-конфликт в
  BACKLOG.md, от которого уходим (design §216).
- **Первый прогон в derived-проекте.** BACKLOG.md ещё без управляемого
  блока — `sync` сам вставляет его (self-bootstrap), не разрушая
  вводную прозу (правила формата, scope-guard).

## 3. Functional Requirements

### `dt backlog sync [--force]`

- ДОЛЖНА: собрать из store все **незавершённые** задачи — статусы `todo`,
  `doing`, `review`; исключить `done` и `dropped`.
- ДОЛЖНА: упорядочить их **по ID по возрастанию** (стабильно,
  статус-независимо).
- ДОЛЖНА: отрендерить каждую задачу одной строкой с заголовком,
  зависимостями и ссылкой на спеку (точный формат — §5, развилка C).
- ДОЛЖНА: записать результат в `BACKLOG.md` **основной рабочей копии**
  (`repo_root/BACKLOG.md`), обновляя только управляемый блок между
  маркерами и сохраняя окружающую ручную прозу (развилка A).
- ДОЛЖНА: **отказываться работать не на основной ветке** без `--force`:
  текущая ветка ≠ локальная default-ветка (`default_base_branch`, T036) →
  ошибка exit 1 с подсказкой про `--force`. Detached HEAD (ветки нет) →
  тоже отказ без `--force`.
- ДОЛЖНА: быть идемпотентной — повторный `sync` без изменений в store даёт
  побайтово тот же файл.
- МОЖЕТ: `--force` — выполнить синхронизацию несмотря на неосновную ветку
  (аварийный люк; штатно — только на main).
- НЕ ДОЛЖНА: делать сетевые вызовы; трогать что-либо вне управляемого блока
  BACKLOG.md; читать/писать чужие worktree.

### Функция расхождения (для T051, развилка B — строим сейчас)

- ДОЛЖНА: чистая `backlog_divergence(store, backlog_text) → (added, removed)`:
  `added` — незавершённые задачи store, отсутствующие в управляемом блоке
  BACKLOG.md («заведено», +N); `removed` — ID из блока, которых нет среди
  незавершённых («завершена»/выброшена, −M). Оба списка — по возрастанию ID.
- ДОЛЖНА: парсить ID из **управляемого блока** (не всего файла) — только его
  ведёт `sync`.
- НЕ ДОЛЖНА (в T040): иметь CLI-команду или резолвить путь «основной рабочей
  копии» — это вшивает `dt context` (T051). T040 отдаёт готовую чистую
  функцию; T051 подаёт ей текст BACKLOG.md основной копии (design §880).

### Общее

- ДОЛЖНА: неинтерактивность; `TaskError`/`DtHomeError`/`OSError` → stderr +
  exit 1 без traceback (образец `_run` из `task_cli`).
- ДОЛЖНА: чистое ядро (сборка модели + рендер + вставка блока) — **typer-free
  И git-free**; git-контекст (repo_root, current_branch, base) подаётся
  параметром из `paths.py`. Повторяет расслоение T035/T037.

## 4. Success Criteria

- `dt backlog sync` на main c непустым store: BACKLOG.md содержит все
  незавершённые задачи по возрастанию ID, без указания статуса; `done`/
  `dropped` отсутствуют.
- Перевод задачи `todo → doing → review` (без заведения/закрытия) и повторный
  `sync` → BACKLOG.md **не меняется** (статус-независимость).
- `sync` на ветке `T0NN-...` без `--force`: exit 1, файл не тронут, внятная
  ошибка с упоминанием `--force`. С `--force` — синхронизирует.
- Повторный `sync` подряд идемпотентен (нет diff).
- BACKLOG.md без управляемого блока: первый `sync` вставляет блок, вводная
  проза сохранена.
- 4 гейта зелёные; coverage ≥ 80% на новом коде.

## 5. Key Entities

- **backlog item** — проекция записи задачи в строку BACKLOG.md: ID,
  заголовок, `deps`, `spec`. Статус НЕ отображается (§215). Порядок — по ID.
- **управляемый блок** — регион BACKLOG.md между маркерами-комментариями
  `<!-- dt:backlog:begin -->` … `<!-- dt:backlog:end -->`. Всё вне блока —
  ручная проза, `sync` её не трогает. Маркеры self-bootstrap: нет → вставить.
- **default-ветка** — локальная основная ветка (`default_base_branch`, T036:
  `origin/HEAD`→`main`, иначе `main`/`master`, иначе `main`). Эталон «на
  основной ли мы ветке».
- **строка формата задачи** (развилка C) — предлагаемый вид:
  `- **T034** — <title> (deps: T033; spec: specs/T034-…/spec.md)`, где
  `deps`/`spec` опускаются, если пусты.

## 6. Assumptions & Constraints

- `$DT_STORE` резолвится из git-common-dir (T033) — одинаков из любого
  worktree; но **сам файл** BACKLOG.md пишется в `repo_root` текущей копии,
  а штатно `sync` идёт только на основной копии (main-ветка).
- «Основная ветка» проверяется по **имени локальной default-ветки**, а не по
  тому, основная ли это рабочая копия. На практике main обычно вычекан в
  главной копии — совпадает.
- Строка расхождения (design §217, «BACKLOG.md отстаёт: +N/−M») — **не** в
  этой задаче: её потребитель `dt context` (T051). См. Out of Scope,
  развилка B.
- На самом dreamteam store пуст до `dt migrate tasks` (T042) — `sync` на нём
  не гоняем (снёс бы ручной BACKLOG.md-роадмап). Тесты — на temp-store.
- `git` в PATH; вне git без `DT_HOME` — внятная ошибка (T033).

## 7. Out of Scope

- **Отображение** строки расхождения и резолв пути «основной рабочей копии» —
  T051 (`dt context`). T040 строит саму чистую функцию `backlog_divergence`
  (развилка B), но не даёт ей CLI и не решает, из какого файла читать.
- `dt migrate tasks` (парсинг существующих BOARD/BACKLOG, `.bak`, удаление
  BOARD.md) — T042. T040 — только генерация из уже существующего store.
- Догфудинг на самом dreamteam (перевод его BACKLOG.md под управление sync) —
  часть T042, не здесь.
- Группировка по эпикам, роадмап-проза, исторические комментарии — остаются
  ручной прозой вне управляемого блока; `sync` их не генерирует.
- Правка derived-шаблонов `template/i18n/*/BACKLOG.md` под маркеры — не нужна:
  `sync` self-bootstrap вставляет блок при первом прогоне.

## Clarify (3 развилки согласованы опросником 2026-08-01)

### Resolved

- **A. Границы записи** → «Управляемый блок между маркерами». `sync` правит
  только регион `<!-- dt:backlog:begin -->` … `<!-- dt:backlog:end -->`,
  сохраняя вводную прозу (правила формата, scope-guard). Маркеров нет →
  вставляет (self-bootstrap). Отвергнута полная регенерация: она уничтожила бы
  ручной роадмап/эпики/историю (у самого dreamteam — критично).
- **B. Функция расхождения** → «Построить сейчас (по дизайну)». Чистая
  `backlog_divergence` реализуется в T040 с тестами, хотя её потребитель
  `dt context` (T051) ещё не готов — следуем декомпозиции дизайн-карточки T008.
  CLI-команды у неё в T040 нет (нечему потреблять) — только чистая функция.
- **C. Формат строки** → «deps/spec в скобках, дата created»:
  `- **T040** — [2026-07-30] <title> (deps: T034; spec: specs/T040-…/spec.md)`.
  Дата = `created` записи (совпадает с текущим шаблоном `[<date>]`); `deps`/
  `spec` опускаются, если пусты; дата опускается, если `created` не задана.

## Analyze (Claude)

- 🟢 **A1. Расслоение.** Новый чистый модуль `dt/backlog.py` (typer-free И
  git-free): `backlog_items` (проекция store), `render_item`/`render_block`,
  `sync_backlog(existing_text, items) → new_text`, `parse_block_ids`,
  `backlog_divergence`. git-контекст (repo_root, current_branch, base) добывает
  обёртка `backlog_cli.py` из `paths.py` и подаёт в чистое ядро. Повторяет
  T035/T037.
- 🟢 **A2. Идемпотентность.** `sync_backlog` заменяет регион между маркерами
  через regex с **функцией**-заменой (не строкой) — обратные слэши/`\g` в
  заголовках не интерпретируются. Повторный прогон без изменений store даёт
  тот же байт-в-байт файл. Пустой store → пустой блок (только маркеры).
- 🟡 **A3. Self-bootstrap вставки.** Маркеров нет → блок дописывается в конец
  файла (после `rstrip('\n')` + пустая строка). Не под `## Items`
  прицельно — детерминированно и не корёжит произвольный файл; для derived-
  шаблона это конец файла с плейсхолдер-комментарием, приемлемо. Тонкая
  вставка под `## Items` — возможный follow-up, не MVP.
- 🟢 **A4. Порядок по ID — числовой.** Сортировка по `int(id[1:])`, не по
  строке: строковая ломается на разной ширине (`T1000` < `T200`). ID
  валидирован `T[0-9]{3,}` (T034), парс int безопасен.
- 🟢 **A5. Guard основной ветки.** `current_branch != default_base_branch()`
  (T036) без `--force` → exit 1 с подсказкой. Detached HEAD (branch=None) и
  «вне git» (repo_root=None) → тоже отказ без force; с `--force` вне git всё
  равно нет repo_root для записи → внятная ошибка. `default_base_branch`
  офлайновый, сети не трогает.
- 🟢 **A6. Статус-независимость.** Блок несёт `todo`/`doing`/`review` без
  статуса, по ID. Перевод статуса среди незавершённых не меняет ни множество,
  ни порядок → файл побайтово тот же (success-критерий).
- 🟢 **A7. Расхождение = множества, не порядок.** `added = unfinished(store) −
  ids(block)`, `removed = ids(block) − unfinished(store)`. Парс ID из блока
  регуляркой `\*\*(T[0-9]{3,})\*\*`. Оба списка сортируются числовым ключом.
  Чужой текст вне блока на расхождение не влияет.
- 🟢 **A8. Запись в основную копию.** `sync` пишет `repo_root/BACKLOG.md`
  текущего worktree; штатно идёт на main-ветке (обычно = основная копия), так
  что «current worktree» и «main working copy» совпадают. Нюанс «читать блок
  основной копии из чужого worktree» относится только к T051-потреблению
  `backlog_divergence` и в T040 не решается (A1/B).
- 🟢 **A9. Догфудинг отложен.** На самом dreamteam store пуст (до T042) —
  `sync` не гоняем на его BACKLOG.md (снёс бы роадмап). Все тесты — на
  temp-store/temp-git-репо (fixture образца T039).
