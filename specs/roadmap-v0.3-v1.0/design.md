# Часть 1. Позиционирование

## 1.1 Шестислойная карта рынка и место dreamteam

| Слой | Примеры | dreamteam |
|---|---|---|
| 1. Agent / harness | Claude Code, Codex, OpenCode | **не наш слой** — потребитель |
| 2. Protocol / interop | MCP, ACP | не наш слой (см. 1.2) |
| 3. Workspace | Claude Squad, cmux, Orca | **явно не наш слой** |
| 4. Orchestration / state | Gas Town + Beads, Agent Orchestrator | **ядро dreamteam** |
| 5. Sandbox / runtime | Anthropic sandbox-runtime, E2B, Daytona | конфигурируем, не строим (E3) |
| 6. IDE platform | Theia | не наш слой |

Плюс слой, которого в статье нет и который dreamteam занимает целиком:

**Слой 0 — methodology-as-code:** конвенции проекта, ритуалы, чек-листы и правила ревью, распространяемые как версионируемый шаблон с трёхсторонним слиянием в производные проекты.

## 1.2 Решение: только Claude Code

dreamteam не претендует на нейтральность к вендору. Целевой harness — Claude Code, и только он. Механизмы интеграции (`.claude/settings.json`, hooks, slash-команды, subagent-определения, statusline, восстановление сессий) используются напрямую, без слоёв абстракции.

**Что теряем.** Смена harness обесценит интеграционный слой. Методика как текст при этом уцелеет — она не зависит от того, кто её исполняет.

**Дешёвая страховка.** Методика разбивается на секции-файлы (E2). Это нужно само по себе — для рендеринга slash-команд и определений ролей, — а заодно оставляет шов: вторая цель, если понадобится, будет добавлением адаптера, а не разбором монолита. Адаптеров сейчас не пишем, абстракций «на будущее» не вводим.

## 1.3 Тезис

Статья формулирует четыре свойства, дающие устойчивую позицию: нейтральность, жизненный цикл, безопасность, устойчивое состояние. Нейтральность сознательно отдаём. dreamteam владеет **устойчивым состоянием** и **слоем 0**; стратегия — укрепить стык слоёв 0 и 4, **не спускаясь на слой 3**.

Уникальный актив, которого нет ни у одного проекта из обзора: `dt update` — механизм эволюции самой методики с распространением в уже созданные проекты. Диспетчеры этого не умеют, потому что не хранят методику как артефакт.

## 1.4 Anti-scope

Не делаем, вне зависимости от соблазна:

- **диспетчер сессий:** всё, что опрашивает, отображает или контролирует состояние запущенных агентских процессов. Граница проходит не по наличию интерфейса, а по тому, знает ли инструмент о процессах (см. E10);
- собственная песочница, контейнерный runtime, microVM-обвязка;
- meta-harness / унифицированный API поверх нескольких агентов;
- облачный сервис, БД, резидентный демон, фоновой процесс, переживающий терминал;
- автономный цикл «правь пока CI не позеленеет» без лимитов и без человека перед merge;
- **абстракция над системами сборки** — вынесение методики из-под Python с профилями под npm, cargo, go;
- любые заявления о кратном ускорении без собственного замера.

Обоснование: перечисленное либо воспроизводится за выходные, либо поглощается вендором в один релиз, либо требует инфраструктуры, несопоставимой с ресурсом одного мейнтейнера.

**Отдельно об абстракции над системами сборки.** Соблазн отделить слой 0 от инструментального понятен, но методика насквозь пропитана инструментальными деталями: pre-push contract — это конкретные `ruff check` / `mypy src` / `pytest --cov-fail-under=80`, защита от озеленения оперирует `@pytest.mark.skip` и `xfail`, профиль workspace — это `[tool.uv.workspace]`. Разделение дало бы не «чистую методику», а вторую систему с профилями под каждый экосистемный стек.

Цена отказа низкая: на не-Python проект можно сделать `dt apply` и ответить `[k]eep` на конфликтах инструментальных файлов. Методические файлы приедут, `pyproject.toml` не тронется; останется руками поправить секцию pre-push. Это правка одной секции, а не архитектурная работа.

## 1.5 Принцип: формалистику ведёт агент

**Человек не вводит команд `dt`. Их вызывает агент.**

Человек говорит на естественном языке: «помнишь задачу про курсор в полноэкранном режиме? найди и давай сделаем». Поиск задачи, смена статуса, создание ветки и worktree, ведение реестра сессий, переименование окна — делает агент.

Три следствия, обязательные для всего ниже:

1. **Ни одно требование не перекладывается на человека из-за ограничений инструмента.** Если агент чего-то не может — например, переименовать собственную сессию, — это повод спроектировать иначе, а не обязать человека.
2. **Каждая команда `dt` пригодна для вызова агентом:** неинтерактивна, быстра, с `--json` на выходе, с внятным кодом возврата.
3. **Одно намерение — одна команда.** Если начало работы над задачей требует четырёх вызовов, нужна одна команда, делающая все четыре.

Физические действия человека: открыть терминал и запустить `claude` без флагов. При восстановлении после перезагрузки — один вызов `dt resume --tmux`.

## 1.6 Где живёт состояние

Требование «состояние переживает сессию» не означает «состояние лежит в git». Смешение порождает конфликты слияния на волатильных данных и делает картину параллельной работы принципиально несобираемой: файлы под контролем версий существуют в каждом worktree в своей редакции.

| Слой | Где | Что |
|---|---|---|
| **Оперативный** | `$DT_HOME/store/`, далее `$DT_STORE` | записи задач, счётчик ID, реестр сессий, Handover, привязки |
| **Долговременный** | репозиторий | BACKLOG.md, CHANGELOG.md, DECISIONS.md, CONCEPT.md, `specs/` |
| **Рабочие копии** | `$DT_HOME/worktrees/<branch>` | worktree задач, создаются и удаляются автоматически |
| **Представление** | нигде не хранится | графическая доска (E10), вывод `dt board` |

**Единый корень:**

```
$DT_HOME = ${DT_HOME:-<main-worktree>.dt}

myproject.dt/
  store/
    tasks/T001.md …
    counter
    sessions/T001.json …
    by-worktree/<slug>/current-task
    by-worktree/<slug>/context.line
    test-baseline
  worktrees/
    T034-cursor-fullscreen/
```

`<main-worktree>` — корневой каталог основной рабочей копии, то есть родитель общего `.git`: `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`. Из любого worktree вычисление даёт один и тот же результат, поэтому worktree-независимость получается по построению.

`<slug>` — восемь символов sha1 от абсолютного пути worktree. Нужен потому, что `current-task` и `context.line` описывают **конкретную рабочую копию**, а не репозиторий: две параллельные сессии в разных worktree затирали бы друг друга, если бы файл был один.

Почему каталог-сосед, а не другие варианты:

- **не внутри `.git/`** — прячет состояние там, где его никто не ищет, и выводит из-под резервного копирования проекта; для рабочих копий вдобавок ломает git-инструменты и редакторы;
- **не внутри репозитория** — состояние попало бы под контроль версий (то, от чего уходим), а вложенные рабочие копии — под обход ruff, mypy, pytest и ripgrep;
- **не в общемашинном каталоге** — всё, относящееся к проекту, разъезжается по диску и не попадает в резервную копию вместе с ним.

`DT_HOME` — аварийное переопределение. Для голого репозитория корень берётся от самого common-dir; случай краевой и покрывается переопределением.

**Следствия, принятые сознательно:**

- **BOARD.md исключается из репозитория.** Это версионируемый снимок волатильных данных: шум в истории, конфликты на пустом месте, необходимость проверять синхронность. Временное расхождение картины снимается при слиянии PR.
- **BACKLOG.md и CHANGELOG.md остаются в git** и несут всю долговременную память. Переход между слоями — осознанное действие, а не автоматическое зеркалирование.
- Всё, что дольше недели имеет значение, обязано быть в долговременном слое. Оперативный слой можно потерять целиком без потери проекта.
- Резервное копирование требует копировать `<repo>/` и `<repo>.dt/` вместе.

# Часть 2. Эпики v0.3

## E1. Оперативный слой состояния задач

**Проблема.** BOARD.md/BACKLOG.md читаются человеком, но: агент парсит markdown-канбан ненадёжно; зависимостей между задачами нет; параллельная правка одного файла даёт конфликт слияния; нет ответа на «что можно брать в работу прямо сейчас»; состояние под контролем версий существует в каждом worktree в своей редакции, поэтому картина параллельной работы нигде не собирается целиком.

### Формат записи

```yaml
---
id: T007
title: Ввести оперативный слой состояния задач
status: doing          # todo | doing | review | done | dropped
deps: [T003, T005]     # блокирующие задачи
parent: T004           # задача, из обсуждения которой родилась эта
spec: specs/T007-task-state/spec.md   # путь относительно корня репозитория
branch: T007-task-state
pr: 42
tags: [core, cli]
created: 2026-07-29
updated: 2026-07-29
---

Свободный markdown: контекст, критерии приёмки, заметки.

## Handover
…
```

Поля `worktree` нет: где лежит рабочая копия, знает git.

### CLI

| Команда | Поведение |
|---|---|
| `dt task new "<title>" [--deps …] [--blocks …] [--parent T007] [--json]` | выделяет номер, создаёт запись |
| `dt task find "<фраза>" [--json]` | поиск по заголовкам, телу, тегам, веткам |
| `dt task start T007` | статус → `doing`, ветка, worktree, привязка, окно tmux, `--json` |
| `dt task move T007 <status>` | меняет статус, обновляет `updated` |
| `dt task split T007 "<title>"` | создаёт задачу с `parent: T007` |
| `dt task ready [--json]` | задачи в `todo`, у которых все `deps` в `done` |
| `dt task show T007 [--json]` | вывод для человека и для агента |
| `dt task check` | валидация целостности |
| `dt board` | текстовое представление доски в терминал |
| `dt backlog sync` | перестраивает BACKLOG.md; только на основной ветке |
| `dt state export <file>` / `import <file>` | перенос между машинами |
| `dt worktree path/root/list/prune` | размещение и жизненный цикл рабочих копий |
| `dt migrate tasks` | разовый перевод проекта на новый слой |

**Выдача ID.** Счётчик — единственный файл `counter`, инкремент через создание с `O_EXCL`. Хранилище одно на репозиторий, параллельных копий не существует, поэтому коллизии номеров невозможны по построению.

### Размещение worktree

Путь вычисляется, а не выбирается: `$DT_HOME/worktrees/<branch>`. Для репозитория `~/projects/myproject` задача T034 получает `~/projects/myproject.dt/worktrees/T034-cursor-fullscreen`.

**Путь нигде не хранится.** Фактическое расположение берётся из `git worktree list --porcelain` по имени ветки. Поэтому worktree, созданный вручную в другом месте, продолжает работать, а устаревших записей о путях не бывает в принципе.

| Команда | Поведение |
|---|---|
| `dt worktree path T007` | вычисленный путь для создания либо фактический из `git worktree list` |
| `dt worktree root` | `$DT_HOME/worktrees` для данного репозитория |
| `dt worktree list` | сопоставление с задачами; отдельно — «осиротевшие» без задачи |
| `dt worktree prune` | удаляет worktree задач в `done` / `dropped` со слитыми ветками |

`prune` **никогда** не удаляет каталог с незакоммиченными изменениями или неслитой веткой — такие пропускаются с перечислением причин. `dt resume` упоминает число подлежащих очистке одной строкой, ничего не предпринимая.

### Валидация

`dt task check` проверяет: отсутствие циклов в `deps`, целостность ссылок `parent` и `blocks`, отсутствие ссылок на несуществующие ID.

**Существование файлов спек проверяется мягко.** Путь в поле `spec` относителен корня репозитория, но сама спека может существовать только на ветке своей задачи и отсутствовать в текущем worktree. Поэтому отсутствие файла — предупреждение, а не ошибка; ошибкой оно становится только если ветка задачи в данный момент выгружена и файла в ней всё равно нет.

### Создание каталога

`$DT_HOME` с подкаталогами создаётся молча при первом вызове любой команды, которой он нужен. Никаких вопросов и никакого отдельного шага — операция идемпотентна. Единственный вывод — одна информационная строка в stderr в момент самого первого создания, с указанием пути. При недоступном для записи родительском каталоге — внятная ошибка с подсказкой про `DT_HOME`.

Это не следует путать с `dt migrate tasks`: каталог создаётся автоматически, а перенос данных из BOARD.md — разовая явная команда.

### Перенос состояния между машинами

`dt state export <file>` выгружает **только записи задач и счётчик**. Реестр сессий и привязки по worktree не переносятся: они описывают конкретную машину, а `session_id` чужой машины бесполезен — соответствующего транскрипта там нет.

`dt state import <file> [--on-conflict skip|overwrite]` без флага прерывается со списком конфликтующих ID (конвенция та же, что у существующей `dt apply`). После импорта счётчик выставляется в максимум из локального и наибольшего импортированного номера.

### Связь с долговременным слоем

- **BACKLOG.md статус-независим.** Перечисляет все незавершённые задачи — `todo`, `doing`, `review` вперемешку — без указания статуса, в стабильном порядке по ID: заголовок, зависимости, ссылка на спеку. Файл меняется только когда задача заведена, завершена, переименована или переосмыслена; переход `todo → doing → review` не меняет в нём ни байта. Git хранит, **что мы собираемся делать**, оперативный слой — **где это сейчас**.
- **`dt backlog sync` выполняется только на основной ветке**, на ветке задачи отказывается без `--force`. Иначе две ветки с новыми задачами дают конфликт слияния в BACKLOG.md — ровно то, от чего уходим. Практически это планирование и возвращение на основную ветку после слияния PR.
- **Расхождение отслеживается мягко.** `dt context` сообщает его одной строкой: «BACKLOG.md отстаёт: +3 заведено, −1 завершена». Сравнение идёт с BACKLOG.md **основной рабочей копии**, а не текущего worktree, — иначе на любой давно отведённой ветке расхождение показывалось бы ложно. Жёсткой проверки в pre-push нет: валить push из-за бухгалтерии — плохой обмен.
- Завершение задачи фиксируется записью в CHANGELOG.md. Это и есть долговременный след сделанного; `status: done` — лишь текущее положение дел.
- Спека живёт в `specs/` под контролем версий, запись задачи хранит на неё путь.

### Критерии приёмки

1. Запись, созданная в одном worktree, немедленно видна из всех остальных без слияния и без каких-либо действий.
2. Два агента, работающие параллельно, не создают git-конфликтов состоянием: состояние в git не попадает вовсе.
3. Две параллельные сессии в разных worktree не затирают привязки и строки статуса друг друга.
4. `dt task ready --json` даёт агенту достаточный ответ на «что дальше».
5. `dt task check` подключён в pre-push по образцу `scripts/translate_check.py`.
6. `dt migrate tasks` парсит существующие BOARD.md/BACKLOG.md, создаёт записи, оставляет `.bak`; BOARD.md затем удаляется из репозитория одним коммитом.
7. Удаление всего каталога `$DT_HOME` не разрушает проект: BACKLOG.md, CHANGELOG.md и спеки на месте, теряется только текущее положение дел.

### Риск, принимаемый сознательно

Оперативный слой не приезжает с `git clone`, не уходит на `git push` и не синхронизируется между машинами. Митигация двойная: `dt state export/import` для переноса и правило, что всё заслуживающее памяти дольше текущей недели обязано быть в BACKLOG.md, CHANGELOG.md или спеке.

### Внедрение

Формального пилота с критериями отката не проводим. Новый слой обкатывается на самом dreamteam — единственном проекте, где мейнтейнер одновременно заказчик и потребитель, а поломка ничего не стоит. Это же честный догфудинг: методика, не выдерживающая собственной разработки, в рабочий проект не идёт.

Откат дёшев и остаётся дёшевым: `dt state export`, генерация BOARD.md обратно в репозиторий, задачи как были. Именно потому, что долговременный слой лежит в git отдельно, неудачный эксперимент стоит потраченного времени, а не разрушенного проекта.

**Что сознательно не берём из Beads:** БД, демон, автоматическое извлечение задач из кода и диалога, граф зависимостей с приоритетами. Plain files — вся система хранения.

## E2. Разбиение методики на секции

**Проблема.** CLAUDE.md — монолит. Из него нужно порождать slash-команды (E6), определения ролей (E4) и вкладываемый в сессию контекст (E9); сейчас всё это пришлось бы дублировать.

**Решение.** Источник — `src/dreamteam/template/i18n/<lang>/methodology/*.md`, секции: `scope-discipline`, `git-workflow`, `pre-push`, `code-review`, `rituals`, `sessions`. CLAUDE.md собирается из них при рендеринге; отдельные секции переиспользуются в командах и ролях.

**Языки сокращаются до `ru` + `en`.** Источник остаётся русским, английский — единственный перевод. `fr`, `de`, `zh` удаляются одним коммитом с записью в DECISIONS.md: пользователей нет, а стоимость сопровождения растёт линейно по числу секций — шесть секций на пять языков дали бы тридцать файлов, обязанных оставаться согласованными, и налог этот платится при каждой правке того, что правится чаще всего. Возврат возможен тем же механизмом, если появится спрос.

**`source_hash` проверяется на релизе, а не на каждый PR.** `scripts/translate_check.py` переезжает из основного CI-прогона в `scripts/publish.sh`: рассинхрон блокирует публикацию, но не мешает работать.

**Позиционирование в README.** Публичный репозиторий, MIT и пакет на PyPI сохраняются: они не стоят ничего, а `uvx --from dreamteam-cli dreamteam init` разворачивает инструмент на новой машине без возни с окружением. Меняется только текст: dreamteam описывается как личный инструмент методики для Claude Code — без обещаний поддержки, обратной совместимости и вендорной нейтральности.

**Критерии приёмки:** правка секции распространяется во все производные артефакты одним `dt update`; собранный CLAUDE.md эквивалентен текущему по содержанию; CI проверяет наличие всех обязательных секций.

**Явно не входит:** генерация AGENTS.md, правил Cursor, инструкций Copilot и любых других целей.

## E5.1. Защита от озеленения тестов

**Проблема.** Агенту, которому сказано «почини тесты», заглушить тест дешевле, чем найти причину. Это обычное поведение при обычной работе, а не риск гипотетической автоматической петли, — поэтому защита нужна независимо от того, появится ли когда-нибудь CI-цикл.

**Решение.** Проверка в pre-push, из той же семьи, что и `dt task check`:

- число собираемых тестов (`pytest --collect-only -q`) не уменьшилось;
- новые `@pytest.mark.skip` / `@pytest.mark.xfail` не появились без соответствующей записи в DECISIONS.md;
- порог `--cov-fail-under` не понижен правкой конфигурации.

**Откуда берётся базовое число.** Не прогоном на merge-base — это удваивает время pre-push. База хранится в `$DT_STORE/test-baseline` и обновляется после каждого успешного push. Если файла нет (первый запуск, свежий клон), проверка пропускается и база записывается молча.

**Аварийный выход.** Проверка эвристическая: честный рефакторинг, сливающий несколько тестов в один параметризованный, может законно уменьшить счётчик. Разблокировка та же, что и для `skip`: запись в DECISIONS.md с объяснением. Обходного флага без записи нет, иначе агент найдёт его первым же.

**Критерии приёмки:** ловит удаление теста, добавление `skip` без обоснования и понижение порога покрытия; сообщение называет конкретные пропавшие тесты, а не только разницу чисел.

## E6. Ритуалы как исполняемые команды

**Проблема.** clarify/analyze/review/retro описаны в CLAUDE.md, то есть выполняются, только если агент вспомнил про них.

## E9. Связывание сессий и задач

**Проблема — две симметричные потери ориентации.**

*Человек.* После перезагрузки живых процессов не остаётся. Транскрипты на диске есть, но что к какой задаче относится и в каком каталоге запускать — восстанавливается вручную. Говорящие имена терминальных окон помогают частично и не переживают reboot.

*Агент.* Договорились об очистке контекста, составили памятку — в новой сессии на «продолжаем задачу» приходит вопрос «какую именно?». Памятка есть, но ничто не обязывает её прочитать: связь «сессия ↔ задача» нигде не зафиксирована машинно.

Обе половины — один дефект: **нет ключа, связывающего исполнение с задачей и переживающего смерть процесса.**

### E9.1 Выбор ключа

| Кандидат | Переживает reboot | Переживает `/clear` | Уже есть в методике |
|---|---|---|---|
| session id | да (файл), но процесс — нет | новый id | нет |
| имя сессии | да | да | нет |
| **ветка / worktree** | да | да | **да** (`T<NNN>-slug`) |

Ветка уже кодирует номер задачи по действующему соглашению об именовании: `git branch --show-current` → `T<NNN>` → `$DT_STORE/tasks/T<NNN>.md`, без единого дополнительного записанного байта.

**Порядок разрешения задачи** — единый для всех команд и хуков:

1. переменная окружения `DT_TASK`;
2. имя текущей ветки, если совпадает с `T\d{3}`;
3. `by-worktree/<slug>/current-task` — для работы вне ветки задачи;
4. не определено → сессия **непривязанная**, и это нормальный режим, а не ошибка.

### E9.2 Опознание задачи по человеческой фразе

Именование сессий как требование **снято**: агент не может переименовать собственную сессию (`/rename` — клиентская команда, разворачивается до того, как модель что-либо видит; документированного внешнего интерфейса нет), а значит соглашение «имя сессии = ID задачи» неизбежно легло бы на человека и нарушило 1.5. Вместо него — автоматический реестр (E9.4).

**`dt task find "<фраза>"`** — поиск по заголовкам, телу, тегам и именам веток; нормализация и совпадение по токенам с весами: заголовок выше тела, активные статусы выше `done`. Никаких эмбеддингов и внешних сервисов: корпус — десятки файлов.

**Сценарий целиком:**

> — Помнишь была задачка по изменению вида курсора в полноэкранном режиме? Найди и давай выполним.

Агент вызывает `dt task find "курсор полноэкранный режим" --json`, отвечает словами: «Нашёл T034 „Изменить вид курсора в полноэкранном режиме", статус todo, зависимостей нет. Она?» После подтверждения — `dt task start T034`, одна команда, выполняющая всё: статус, ветка, worktree, привязка, окно tmux, строка статуса, `--json` с путём к спеке и текстом Handover.

Человек не набрал ни одного флага.

**Рождение задачи в разговоре.** Ключевое правило: **создание задачи ничего не делает с текущей сессией.** Четыре случая:

| Случай | Что происходит |
|---|---|
| **Побочная задача** — обсуждали T034, всплыло независимое дело | `dt task new "…" --parent T034` → в backlog, сессия и ветка не меняются |
| **Расщепление** — выяснилось, что T034 на самом деле две задачи | `dt task split T034 "вторая половина"`, текущая сессия остаётся на T034 с урезанным scope; сужение фиксируется в теле задачи |
| **Разведка стала задачей** — из непривязанного обсуждения выкристаллизовалась работа | `dt task new`, затем `dt task start` на новую ветку; история обсуждения остаётся в той же сессии, что и ценно |
| **Блокирующее открытие** — T034 не доделать, пока не сделано новое | `dt task new "…" --blocks T034` → T034 получает зависимость и уходит из `dt task ready` |

**Непривязанная сессия** — легальный режим: обсуждение, разведка, проектирование. Обратное правило («каждая сессия обязана иметь задачу») породило бы фиктивные задачи ради формальности.

### E9.3 `dt context` — ориентация агента

```
dt context [--json] [--hook]
```

Вывод: ID и заголовок задачи, статус, ветка, путь к спеке, текст `## Handover`, блокирующие задачи, номер PR, строка о расхождении BACKLOG.md. Для непривязанной сессии — признак непривязанности и список задач в `doing`, без требований и предупреждений.

**Подключение:** SessionStart-хук в `.claude/settings.json`, вызывающий `dt context --hook`. Хук печатает `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "…"}}` с кодом выхода 0.

Требования к хуку:

- срабатывает на всех значениях `source` (`startup`, `resume`, `clear`, `compact`, `fork`) — сценарий «договорились об очистке» покрывается значением `clear`;
- бюджет вывода не более 2000 символов при документированном лимите 10 000; полный контекст остаётся в записи задачи, в контекст идёт выжимка плюс путь;
- время работы — доли секунды, никаких сетевых вызовов;
- любая ошибка → выход с кодом 0 и пустым выводом; хук никогда не блокирует старт сессии.

**Запрет:** не парсить `~/.claude/projects/**/*.jsonl`. Формат транскриптов объявлен внутренним и меняется между релизами. Только документированные интерфейсы: поля хуков, `--output-format json`, `/export`.

### E9.4 Реестр сессий и восстановление

**Ключевое наблюдение:** SessionStart-хук получает на вход `session_id` и `cwd`. Реестр строится сам, без единого действия человека.

Хук попутно пишет `$DT_STORE/sessions/<TASK_ID>.json`:

```json
{"session_id": "8f2e1c4a-…", "cwd": "/home/u/projects/myproject.dt/worktrees/T034-cursor-fullscreen", "last_seen": "2026-07-29T14:12:03"}
```

**Файл на задачу, а не один общий JSON.** Хуки нескольких параллельных сессий пишут одновременно; общий файл потребовал бы блокировки и всё равно ловил бы гонки на read-modify-write.

**`dt resume`** читает реестр и выдаёт точную команду:

```
dt resume            # таблица: задача, статус, ветка, worktree, команда восстановления
dt resume --tmux     # одноразовый скрипт раскладки
dt resume T034       # команда для одной задачи
```

```
T034  doing   ../myproject.dt/worktrees/T034-cursor-fullscreen   cd <путь> && claude --resume 8f2e1c4a-…
```

Деградация без записи в реестре — `claude --continue`, берущая последнюю сессию в каталоге; при правиле «один worktree — одна задача» результат тот же.

`--tmux` генерирует **скрипт**, который человек читает и запускает: окно на задачу, имя окна = ID задачи, `cd` в worktree, команда восстановления.

**Ограничение.** Транскрипты по умолчанию чистятся через 30 дней (`cleanupPeriodDays`). `dt resume` обязан проверять существование файла сессии и при его отсутствии выдавать `claude` без флагов плюс подсказку прочитать Handover — вместо команды, которая упадёт с ошибкой.

### E9.5 Handover как живая секция

Slash-команда, требующая, чтобы человек её набрал в нужный момент, нарушает 1.5 и хрупка: забыл перед `/clear` — памятки нет.

Секция **поддерживается непрерывно**. Методика предписывает агенту обновлять её при каждом `dt task move`, после завершения осмысленного шага и при любом упоминании человеком паузы, очистки или переключения — «давай очистим», «на сегодня всё», «переключаемся» — то есть по естественной фразе, а не по команде.

```markdown
## Handover
- Сделано: …
- Остановились на: …
- Следующий шаг: …
- Открытые вопросы: …
- Затронутые файлы: …
```

Секция перезаписывается целиком. Она же — то, что `dt context` вкладывает в новую сессию при `source: clear` и `resume`. Slash-команда `/handover` остаётся доступной как ручной триггер, но методика на неё не опирается.

**Страховка от забывчивости.** PreCompact-хук фиксирует время последнего обновления. Если `dt context` при старте видит, что Handover старше последнего коммита в ветке, он вкладывает предупреждение: памятка устарела, восстанови картину по `git log` и диффу. Это честнее, чем молча подсунуть протухшее описание.

### E9.6 Поверхности отображения

| Поверхность | Кто ведёт | Что показывает | Когда обновляется |
|---|---|---|---|
| Реестр сессий | SessionStart-хук, автоматически | задача → session_id → каталог | при каждом старте и резюме |
| Имя окна tmux | агент | что происходит в окне сейчас | при `dt task start` и `dt task move` |
| Statusline | скрипт | задача, статус, ветка | каждый ход |

Имя сессии Claude Code в схеме не участвует. Назвать сессию вручную человек вправе, но ничто на это имя не опирается.

**Имя окна tmux.** `tmux rename-window -t "$TMUX_PANE" T034`. Указание `-t "$TMUX_PANE"` обязательно: сессия агента не обязана быть активным окном. Ручное переименование отключает `automatic-rename`, так что tmux его не перезапишет. **Отсутствие tmux не является ошибкой** — переименование просто пропускается. `tmux rename-window` вносится в allow-лист (E3.1); никакие другие подкоманды tmux не разрешаются. Это единственная операция агента, влияющая на среду за пределами репозитория.

**Statusline.** `.claude/settings.json` содержит `statusLine` типа `command`. На вход скрипту приходит JSON с `session_id`, `session_name`, `cwd`, моделью и данными о контексте.

Statusline вызывается на каждом обновлении сообщений, поэтому запуск Python-процесса там недопустим. Строку пишут в `by-worktree/<slug>/context.line` SessionStart-хук, `dt task start` и `dt task move`; сам statusline — короткий shell-скрипт, вычисляющий `<slug>` от `cwd` и читающий файл. Отсутствие файла → пустая строка и код 0. Отрабатывает быстрее 50 мс и не запускает интерпретатор Python.

### E9.7 Критерии приёмки

1. За весь цикл работы над задачей — от «найди ту задачу про курсор» до слияния — человек не вводит ни одной команды `dt` и ни одного флага `claude`.
2. После перезагрузки `dt resume --tmux` восстанавливает раскладку по всем активным задачам.
3. Сценарий «поработали → „давай очистим" → `/clear` → „продолжаем"» проходит без вопроса «какую задачу?».
4. Задача, созданная агентом посреди сессии, не требует ни переименования сессии, ни смены ветки, ни действий человека.
5. Непривязанная сессия работает без предупреждений и требований.
6. Две параллельные сессии показывают в statusline каждая свою задачу.
7. Устаревшая секция Handover распознаётся и помечается, а не выдаётся за актуальную.
8. Ни один компонент не читает внутренние файлы транскриптов.
9. Отсутствие `dt` в PATH, отсутствие tmux или сломанный хук не мешают работать в проекте.

### E9.8 Риски

- **Ретенция.** Транскрипты чистятся через 30 дней. Актуальный Handover обязателен, а восстановление сессии — удобство, а не источник истины.
- **Раздувание контекста.** Хук, вкладывающий много текста при каждом старте, платится токенами на всех сессиях. Отсюда бюджет в 2000 символов.
- **Зависимость от конкретных флагов Claude Code.** Принята сознательно. Митигация процедурная: перед реализацией сверять флаги и поля хуков по документации, а не по памяти.

## E11. Профиль workspace

**Проблема.** Шаблон предполагает тождество «один репозиторий = один пакет = один набор методических файлов = один pre-push». В uv workspace тождество рвётся, и `dt update` не проходит чисто — то есть механизм распространения методики отказывает там, где нужен больше всего.

**Разбор по слоям.** Разлом проходит только по одному из трёх:

| Слой | В workspace |
|---|---|
| Методика | один комплект на корень; задачи и решения ходят поперёк пакетов, дробить вредно |
| Оперативный слой | на корень по построению; задача может трогать несколько пакетов сразу |
| **Инструментарий** | **вся сложность здесь:** `pyproject.toml` есть у корня и у каждого пакета |

**Решение.** Copier-вопрос `layout` со значениями `single` (по умолчанию) и `workspace`, влияющий **только на инструментальный слой**:

- корневой `pyproject.toml` с `[tool.uv.workspace]` и общими разделами ruff / mypy / pytest;
- пустые `packages/` и `apps/` с README о конвенции;
- pre-push прогоняет линтеры, типы и тесты по всему дереву разом, единый порог покрытия. Раздельные пороги по пакетам отвергнуты: бухгалтерия без пользы, а пакеты в workspace всё равно связаны;
- `dt apply` на существующий workspace распознаёт корневой `[tool.uv.workspace]` и не трогает `pyproject.toml` вложенных пакетов.

Методические файлы, `.claude/`, хуки и `.dt` идентичны в обоих вариантах. `layout` не порождает второй методики — только второй профиль инструментов.

**Критерии приёмки:** `dt init --data layout=workspace` даёт проект, проходящий собственный pre-push сразу после `uv sync`; `dt apply` не изменяет ни одного вложенного `pyproject.toml`; `dt update` проходит без конфликтов; переключение `layout` после создания не поддерживается и сообщает об этом внятно.

## E12. Запуск приложения из правильного каталога

**Проблема.** Просьба «запусти приложение, посмотрю глазами» регулярно приводит к запуску из основной рабочей копии вместо worktree задачи. Правка не действует, поведение старое, полчаса уходит на выяснение, что смотрели не туда.

**Причина, а не симптом.** Основная рабочая копия — единственный путь, который агент знает без вычисления: он виден при старте, лежит в истории диалога и совпадает с именем проекта. Путь до worktree задачи нужно откуда-то взять, а если взять негде — подставляется знакомый. Это отсутствие источника, а не невнимательность, и лечится оно так же, как всё остальное в этом ТЗ: у агента убирается необходимость знать путь.

### E12.1 `dt run`

Команды запуска объявляются в версионируемом `pyproject.toml` — рядом с кодом, который они запускают, и потому могут отличаться между ветками:

```toml
[tool.dreamteam.run]
app = "python -m myapp"
app-debug = "python -m myapp --log-level=debug"
```

```
dt run <name> [-- <доп. аргументы>]
dt run --list
```

**Правила выбора каталога:**

1. задача разрешается тем же порядком, что и везде (`DT_TASK` → ветка → `current-task`);
2. каталог задачи берётся из `git worktree list --porcelain` по имени ветки;
3. текущий каталог уже внутри него — запуск на месте;
4. текущий каталог — **другой** worktree того же репозитория, включая основную копию, → **отказ** с указанием, где задача живёт на самом деле; обход только явным `--here`;
5. сессия непривязанная — запуск в текущем каталоге, с печатью пути.

Перед запуском печатается одна строка: имя цели, разрешённая задача, фактический рабочий каталог. Код возврата процесса пробрасывается наружу, вывод не буферизуется, окружение наследуется целиком (GUI-приложению нужен `DISPLAY`).

**Отказ, а не молчаливый запуск.** Пункт 4 — суть эпика. Тихий запуск из неверного каталога дороже явной ошибки: он выглядит как успех и уводит в отладку не того кода.

### E12.2 Детект расхождения

`dt context` добавляет строку, когда задача привязана, а текущий каталог не совпадает с её worktree: «сессия в основной рабочей копии, задача T034 живёт в …». Срабатывает при старте сессии, то есть до первой ошибки, а не после.

Statusline показывает базовое имя каталога рядом с ID задачи — расхождение становится видно и человеку, без всяких команд.

### E12.3 Страховка на уровне разрешений

Методика предписывает запускать приложение только через `dt run`. Соблюдение обеспечивается PreToolUse-хуком из E3.1: команда Bash, совпадающая с одной из объявленных целей и выполняемая не через `dt run`, отклоняется с подсказкой. Хук эвристический и потому дополняет `dt run`, а не заменяет его.

### E12.4 Критерии приёмки

1. `dt run app` из основной рабочей копии при привязанной задаче не запускает ничего и сообщает, где задача.
2. `dt run app` из worktree задачи запускает и печатает разрешённый каталог.
3. Код возврата приложения доходит до вызывающего без изменений.
4. Отсутствие секции `[tool.dreamteam.run]` даёт внятное сообщение со примером конфигурации, а не трассировку.
5. Расхождение каталога и задачи видно в выводе `dt context` и в statusline.

# Часть 3. Эпики v0.4 — v0.5

## E3. Слой политики и честная документация границ

**Проблема.** Слово «изоляция» девальвировано. Производный проект запускает агента с полным доступом к домашней директории, ключам и сети.

**E3.1 Конфигурация разрешений.** Шаблонный `.claude/settings.json`:

- deny: чтение `.secrets`, `~/.ssh`, `~/.aws`, `.env`;
- deny: `git push --force`, push в `main` / `master`;
- deny: `curl … | sh`, `rm -rf` вне рабочего каталога;
- allow: `tmux rename-window` и только она из подкоманд tmux;
- ask: сетевые запросы за пределы whitelist;
- PreToolUse-хук: запрет записи вне разрешённой области. Область — текущий worktree и `$DT_HOME` целиком;
- PreToolUse-хук: отклонение команд запуска, совпадающих с целями `[tool.dreamteam.run]`, если они выполняются не через `dt run` (страховка для E12; эвристика, дополняющая команду, а не заменяющая её).

**E3.2 Профиль изоляции** — copier-вопрос `sandbox_profile` (`none` | `devcontainer` | `sandbox-runtime`). Никакой собственной реализации: генерируем конфиг под существующие механизмы.

**E3.3 `SECURITY-NOTES.md`** — таблица «что реально даёт каждый механизм»: worktree защищает ветки, не хост; контейнер даёт файловую границу, но bind mounts и docker socket её ломают; microVM сильнее, но дороже. dreamteam **не** обеспечивает изоляцию, он конфигурирует чужие механизмы и документирует их пределы.

## E4. Роли как артефакты, а не как флот

Рендерить `.claude/agents/*.md` из секций методики. Минимальный набор, **не больше четырёх**:

| Роль | Назначение |
|---|---|
| `reviewer` | код-ревью по чек-листу из методики, только чтение + комментарий |
| `spec-writer` | ритуалы clarify/analyze, спека по `specs/spec-template.md` |
| `test-writer` | тесты по спеке до реализации |
| `translator` | ru → en с обновлением `source_hash`, перед релизом |

Gas Town с двадцатью ролями — демонстрация предела, а не образец. Каждая роль стоит контекста и токенов; роль оправдана, только если у неё свой набор инструментов и своя зона ответственности, отличная от главного агента.

## E5.2. Брифинг по CI

| Команда | Поведение |
|---|---|
| `dt ci status [T007]` | через `gh`: состояние PR, упавшие джобы, комментарии ревью |

Агент получает бриф как вход. Автослияние не реализуем: merge остаётся за человеком.

**Условие взятия в работу.** Не по плану, а по факту: если за время работы на v0.3–v0.4 накопится ощущение, что возня с упавшим CI ест время. У соло-разработчика, который сам мержит свои PR, роль курьера объективно меньше, чем в команде.

Лимит попыток и поле `ci_attempts` вводятся **вместе с этой частью, а не раньше**: без брифинга считать нечего.

## E10. Графическая доска

### E10.1 Почему это не противоречит anti-scope

Запрет касается **диспетчера**, а не интерфейса. Граница — знает ли инструмент о запущенных процессах. Доска, рисующая файлы, — проекция. Доска, показывающая, какой агент сейчас думает, — диспетчер.

Вредны три конкретные вещи, в которые доска обычно вырождается:

**1. Второй источник истины.** Доска со своим хранилищем разойдётся с записями задач.
→ Чистая проекция `$DT_STORE/tasks/`. Любая запись идёт через тот же код, что и CLI. Доска не хранит ничего, поэтому терять ей нечего.

**2. Ползучее превращение в диспетчер.** «Покажем, кто ждёт ответа» требует опроса процессов → резидентной части → мониторинга.
→ Доска не знает о процессах. Никогда.

**3. Стоимость второго UI.** Фреймворк, сборка, npm-зависимости, отдельные тесты.
→ Один шаблон в составе пакета, ноль зависимостей, ноль сборки, рендеринг из той же модели, что и текстовый `dt board`.

### E10.2 Никаких сгенерированных файлов

Статический режим `--html` исключён: любой сгенерированный файл — снимок, расходящийся с задачами при следующей правке. Ровно по этой причине из репозитория убран BOARD.md; заводить вместо него другой снимок бессмысленно.

Шаблон разметки лежит **в пакете `dreamteam`**, а не в производном проекте: агент физически не имеет к нему доступа, исправления приезжают обновлением пакета, в проекте нечему разойтись.

### E10.3 Алгоритм

```
dt board serve [--port 8765] [--open]
```

**Сборка модели** — та же функция, что у текстового `dt board`: прочитать `$DT_STORE/tasks/*.md`, отсеять `dropped`, отсортировать по `updated`. Никакого обхода worktree и слияния редакций: хранилище одно на репозиторий.

| Маршрут | Действие |
|---|---|
| `GET /` | собрать модель → отрендерить шаблон → отдать HTML |
| `GET /api/digest` | хэш от `(путь, mtime, размер)` всех записей |
| `GET /api/tasks` | та же модель в JSON |
| `POST /api/task/<id>/status` | смена статуса |

**Живое обновление.** Страница опрашивает `/api/digest` раз в секунду; хэш изменился → запрашивает `/api/tasks` и перерисовывает. Никаких websockets, SSE, вотчеров и внешних библиотек. Правка задачи агентом в соседнем терминале видна в течение секунды.

**Запись.** `POST` вызывает ту же функцию, что и `dt task move`. Оптимистическая блокировка: клиент присылает `mtime`, каким его видел; при расхождении сервер отвечает `409`, страница обновляется. Это существенно, потому что агент правит те же файлы параллельно.

**Процесс.** Слушает только `127.0.0.1`, живёт на переднем плане, умирает по Ctrl-C. Ни автозапуска, ни unit-файла, ни демонизации.

**Доска не запускает процессов.** Кнопка «открыть в терминале» через `tmux new-window` рассмотрена и отклонена. Она вернула бы три действия к одному, но создала бы единственное место, где dreamteam запускает процесс, — а за запуском немедленно следует «покажи, запустилось ли», затем «а он ещё работает?», затем «убей его». Защита здесь дисциплинарная, а не техническая, то есть работает ровно настолько, насколько соблюдается через полгода. Поэтому запрет абсолютный. Единственное действие карточки — **копировать команду восстановления** в буфер обмена.

### E10.4 Критерии приёмки

1. Доска не создаёт ни одного файла; остановка сервера не оставляет артефактов.
2. Правка записи любым способом отражается на открытой странице в течение секунды.
3. Задачи, идущие в других worktree, видны без действий по синхронизации.
4. Изменение статуса в браузере и `dt task move` идут через один код.
5. Одновременная правка агентом и через браузер не теряет изменений: конфликт обнаруживается и разрешается перечитыванием.
6. Работает без сети и без JS-зависимостей.
7. Сервер не запускает процессов: единственное действие карточки — копирование.
8. В интерфейсе нет ни одного элемента, отражающего состояние запущенных агентов.

# Часть 4. Отложенное

## E7. MCP-сервер

`dt mcp serve` — экспорт `task_ready`, `task_show`, `task_move`, `board_model`, `ci_brief` как MCP-инструментов. Приоритет низкий: CLI и slash-команды покрывают сценарии Claude Code полностью. Браться только если появится конкретное неудобство, которое MCP снимает, — а не ради самого протокола.

## E8. Метрики методики

`dt stats` — локально, без отправки куда-либо: throughput задач по неделям, доля задач с повторным заходом на ревью, доля падений pre-push по типам проверок.

**Требует инструментовки.** Первые две метрики выводятся из полей `created` / `updated` / `status` и считаются задним числом. Третья — нет: сейчас никто не пишет, что и почему упало. Значит вместе с E8 в pre-push добавляется дописывание строки в `$DT_STORE/events.log` (проверка, результат, отметка времени). Без этого метрика невычислима, и браться за неё, не заведя журнал заранее, бессмысленно.

## 5.2 Критерии успеха v1.0

1. На вопрос «что делать дальше» агент отвечает одной командой.
2. Состояние параллельной работы видно целиком из любого worktree, без слияния и без синхронизации.
3. Эволюция методики доезжает до всех производных проектов одним `dt update` — одинаково для однопакетного проекта и для workspace.
4. Ни человек, ни агент не теряют привязку к задаче при перезагрузке системы и при очистке контекста.
5. Задача, родившаяся в разговоре, попадает в систему одной командой и не ломает текущую сессию.
6. В производном проекте задокументировано, что именно запрещено агенту, — а не только что ему «выделен изолированный worktree».
7. Ни один компонент dreamteam не знает о состоянии запущенных агентских процессов.

## 5.3 Решения, подлежащие пересмотру

Каждый пункт дублируется записью в DECISIONS.md.

## 6.4 Замечания к порядку работ

**T010 — точка невозврата.** По зависимостям она готова сразу после T008, но делать её тогда не стоит: BOARD.md будет удалён, а T019–T021 ещё не приедут, и неделю придётся жить без доски и без ориентации в сессиях. Граф разрешает, здравый смысл — нет.

**T018 — хороший первый подопытный.** Не зависит ни от чего, стоит дёшево, и её не жалко провести через всю новую машинерию: завести через `dt task new`, вести через `dt task start`, закрыть записью в CHANGELOG.

**Разрешение на `tmux rename-window`** живёт в E3, то есть в v0.4. До тех пор T007 будет каждый раз спрашивать подтверждения. Если надоест — эту строку из E3.1 можно вытащить в v0.3 отдельной однострочной задачей.

**T024 стоит делать раньше, чем позволяет граф.** Формально он зависит от T019, но это самая частая бытовая ошибка из всех, что закрывает ТЗ, и цена её — потерянные полчаса каждый раз. Как только T004 и T019 закрыты, T024 разумно взять до T020–T023.

**T001 закладывает вычисление `<slug>`,** от которого зависят T007, T019 и T022. Ошибка в нём проявится позже и в трёх местах сразу — стоит покрыть тестами сразу, включая случай двух worktree одного репозитория.
