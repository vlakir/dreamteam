## 1. Overview

Двадцатая по дизайну (карточка T020), репозиторный T052, эпик E9
(`deps: T051`). Замыкает **автоматическую привязку сессии к задаче**: T051
дал `dt context --hook`, который умеет ориентировать агента, но нигде не
фиксирует связь «эта живая сессия ↔ эта задача ↔ этот каталог». T052
добавляет два недостающих звена — **реестр сессий** (файл-на-задачу,
который строится сам при каждом старте сессии) и **шаблонный SessionStart-
хук** в `.claude/settings.json`, вызывающий `dt context --hook`.

Ключевое наблюдение (§362): SessionStart-хук получает на вход `session_id`
и `cwd`. Значит реестр строится **без единого действия человека** — хук
попутно пишет `$DT_STORE/sessions/<TASK_ID>.json`. Позже `dt resume`
(T053) прочитает его и выдаст точную команду восстановления раскладки
после reboot.

## 2. Сценарии использования

- **Реестр строится сам (агент/человек).** Сессия стартует в worktree
  задачи `T034-*`. SessionStart-хук зовёт `dt context --hook`; тот, помимо
  вкладывания контекста, пишет `sessions/T034.json` с `session_id`, `cwd`,
  `last_seen`. Человек не набрал ни одной команды.
- **Восстановление после reboot (задел под T053).** Живых процессов нет,
  но `sessions/T034.json` пережил перезагрузку: `dt resume` (T053) прочтёт
  его и выдаст `cd <cwd> && claude --resume <session_id>`.
- **Непривязанная сессия.** Ветка `main`, нет `DT_TASK`/`current-task`:
  хук по-прежнему отрабатывает (ориентация по §347), но **запись в реестр
  не делается** — ключ реестра это `<TASK_ID>`, а задачи нет. Это штатный
  режим, не ошибка.
- **Параллельные сессии.** Две сессии на разных задачах пишут в **разные**
  файлы (`sessions/T034.json`, `sessions/T041.json`) — гонок на общий файл
  нет по построению (§370).
- **Готовый проект из шаблона.** `dreamteam init my-project` создаёт
  `.claude/settings.json` с уже подключённым SessionStart-хуком —
  привязка сессий работает «из коробки», без ручной настройки.

## 3. Functional Requirements

### Чтение входа хука (`dt context --hook`)

- ДОЛЖНА: читать stdin как JSON SessionStart-хука и извлекать
  `session_id`, `cwd`, `source` (документированные общие поля хука).
- ДОЛЖНА: быть **толерантной** ко входу: пустой stdin, невалидный JSON,
  отсутствие любого поля → не падать; просто нет `session_id` → запись в
  реестр не делается, контекст всё равно вкладывается.
- НЕ ДОЛЖНА: читать `transcript_path` или любые внутренние файлы
  транскриптов (§358, §434); поле `transcript_path` **не документировано**
  для SessionStart и не используется.
- НЕ ДОЛЖНА: различать поведение по `source`: хук отрабатывает одинаково
  на всех значениях (`startup`/`resume`/`clear`/`compact`/`fork`, §353).

### Запись реестра (`sessions/<TASK_ID>.json`)

- ДОЛЖНА: писать `$DT_STORE/sessions/<TASK_ID>.json` **только** когда
  сессия привязана (`ContextModel.task is not None`) **и** `session_id`
  присутствует во входе.
- ДОЛЖНА: содержимое записи — объект с полями `session_id` (строка),
  `cwd` (строка из входа хука; при отсутствии — cwd процесса), `last_seen`
  (tz-aware ISO-8601, требование `flake8-datetimez`; ключ реестра — не
  дата, а «когда последний раз видели эту сессию»).
- ДОЛЖНА: **файл-на-задачу**, не общий JSON (§370): параллельные хуки не
  гоняются, блокировки не нужны.
- ДОЛЖНА: перезаписывать файл целиком (последняя запись побеждает): при
  правиле «один worktree — одна задача» это нормально, `last_seen`
  обновляется.
- ДОЛЖНА: писать **атомарно** (temp-файл в том же каталоге + `os.replace`),
  чтобы параллельный `dt resume` (T053) не прочитал полузаписанный файл.
- ДОЛЖНА: сохранять неизвестные поля не требуется (реестр пишет только
  хук, схема фиксирована); чтение (`read_session_record`, задел под T053)
  толерантно к лишним полям.

### Инвариант «хук никогда не мешает старту»

- ДОЛЖНА: любая ошибка на пути хука (нет store, битый stdin, отказ записи
  реестра, любое исключение) → выход **код 0** и пустой/частичный вывод;
  сессия стартует. (SessionStart в принципе не блокируется — exit 2/любой
  ненулевой лишь показывает stderr; код 0 выбран как чистый путь, при
  котором JSON-payload обрабатывается.)
- ДОЛЖНА: **отказ записи реестра не отменяет вкладывание контекста** —
  сначала собираем контекст и payload, запись реестра — побочный эффект,
  чей провал глотается.

### Шаблонный хук в `.claude/settings.json`

- ДОЛЖНА: `src/dreamteam/template/.claude/settings.json` содержит блок
  `hooks.SessionStart` c одним `type: command`, командой `dt context --hook`.
- ДОЛЖНА: **без** `matcher` — хук срабатывает на всех значениях `source`
  (§353).
- ДОЛЖНА: быть валидным JSON после прохождения через copier (файлы
  рендерятся как Jinja, `_templates_suffix: ""`); в команде нет `{{ }}`,
  файл проходит без изменений.
- НЕ ДОЛЖНА: содержать `statusLine` (T054) или `PreCompact` (T055) — эти
  блоки добавят свои задачи; scope T052 — только SessionStart-хук.

### Разделение слоёв (конвенция репо)

- ДОЛЖНА: чистое ядро реестра — новый модуль `dt/sessions.py`, **typer-free
  И git-free** (как `tasks.py`/`context.py`): сериализация записи + атомарная
  запись/чтение файла. FS-доступ ядру разрешён (образец — `tasks.py`), запрещён
  только `typer`/`git`.
- ДОЛЖНА: обёртка `context_cli.py` добывает stdin/`session_id`/`cwd` и время,
  зовёт ядро; git-факты — по-прежнему из `paths.py`.

## 4. Success Criteria

- Хук со stdin `{"session_id":"S","cwd":"/w","source":"startup"}` в worktree
  `T034-*`: после вызова существует `sessions/T034.json` c
  `{"session_id":"S","cwd":"/w","last_seen":"<ISO+offset>"}`; на stdout —
  валидный `hookSpecificOutput` payload; код 0.
- Тот же хук в непривязанной сессии (ветка `main`): `sessions/` пуст, payload
  всё равно на stdout, код 0.
- Пустой/битый stdin в привязанной сессии: запись реестра **не** делается
  (нет `session_id`), payload на stdout, код 0.
- Смоделированный отказ записи (недоступный `sessions/`): код 0, payload на
  stdout не пропадает.
- Повторный вызов для той же задачи с новым `session_id`: файл перезаписан,
  `session_id` и `last_seen` обновлены.
- `dreamteam init /tmp/x --defaults`: в результате есть
  `.claude/settings.json` с SessionStart-хуком `dt context --hook`, файл —
  валидный JSON.
- `uv build` не даёт duplicate-name warnings из-за нового template-файла.
- Все 4 pre-push проверки зелёные; coverage на `src/` ≥ 80% (новый
  `dt/sessions.py` покрыт).

## 5. Key Entities

- **Запись реестра сессии** (`sessions/<TASK_ID>.json`) — файл-на-задачу.
  Поля: `session_id` (UUID сессии Claude Code из входа хука), `cwd`
  (рабочий каталог сессии, обычно путь worktree задачи), `last_seen`
  (tz-aware ISO-8601 момента последнего старта/резюма). Ключ — `<TASK_ID>`
  в имени файла; в самом JSON `task_id` не дублируется (избыточно).
- **Вход SessionStart-хука** — документированный JSON на stdin:
  `session_id`, `cwd`, `source`, `hook_event_name`. Используем первые три;
  `source` — только для сведения (поведение единообразно).
- **`.claude/settings.json`** (в шаблоне) — файл настроек Claude Code для
  derived-проектов; T052 заводит его с единственным блоком `SessionStart`.

## 6. Assumptions & Constraints

- `dt` есть в PATH derived-проекта (методика это предполагает; §435 —
  отсутствие `dt` не ломает работу, т.к. SessionStart не блокируется).
- Хук исполняется с cwd, равным cwd сессии; git-факты (`git_context`,
  `list_worktrees`) считаются от cwd процесса, как в T051. `cwd` из stdin
  используется как **значение для записи в реестр** (то, что нужно `dt
  resume`), а не для запуска git.
- Транскрипты чистятся через 30 дней (`cleanupPeriodDays`, §388/§439):
  реестр — удобство для восстановления, не источник истины; актуальный
  Handover остаётся обязательным (это забота T055, не T052).
- Формат транскриптов объявлен внутренним; опираемся только на
  документированные поля хука (§358).

## 7. Out of Scope

- **`dt resume`** (чтение реестра, `--tmux`, деградация до `--continue`) —
  T053. Здесь только `write_session_record` + толерантный
  `read_session_record` как задел.
- **Statusline** и запись `context.line` из хука сверх уже сделанного в
  T051 — T054.
- **Handover как живая секция, PreCompact-хук, детект устаревания** — T055.
- **Дифференциация поведения по `source`** (напр. вкладывать Handover
  только на `clear`/`resume`) — T055; здесь хук единообразен.
- **Подключение SessionStart-хука в собственный `.claude/settings.json`
  репозитория `dreamteam`** — store dreamteam пуст до догфудинга
  (`dt migrate tasks`, T042); T052 заводит **шаблонный** хук, не
  догфудит его в самом пакете.
- **Секция методики `sessions`** (правила поведения агента вокруг
  привязки) — T047.

## Clarify (заполняется Claude)

Слепые зоны разрешены против дизайн-документа E9 и проверенного контракта
хука (сверен по официальной документации до реализации, §441). Открытых
вопросов к Разработчику нет — ниже зафиксированы принятые решения.

### Resolved (с ответами)

- **Q (validation): что делать при пустом/битом stdin?** → Толерантно:
  нет `session_id` ⇒ запись реестра пропускается, контекст вкладывается.
  Хук не должен зависеть от наличия входа (ручной вызов `dt context --hook`
  без stdin — легален).
- **Q (edge case): писать ли реестр для непривязанной сессии?** → Нет.
  Ключ реестра — `<TASK_ID>`; без задачи писать некуда и незачем.
- **Q (concurrency): как избежать гонок и рваного чтения?** → Файл-на-задачу
  (§370) снимает межзадачные гонки; атомарная запись (`os.replace`) снимает
  рваное чтение параллельным `dt resume`.
- **Q (errors): отказ записи реестра должен ли ронять хук?** → Нет. Payload
  формируется первым; провал записи глотается, выход код 0.
- **Q (validation): `transcript_path`?** → Не используется и не читается;
  для SessionStart он не документирован, а транскрипты — внутренний формат.
- **Q (data): формат `last_seen`?** → tz-aware ISO-8601 (offset).
  Дизайн-пример был naive-local (`2026-07-29T14:12:03`), но `flake8-
  datetimez` (DTZ) в репо запрещает naive datetime; берём tz-aware (образец
  — `tasks._today()`). Значение переносится между машинами (resume) — offset
  однозначен.
- **Q (integrations): `matcher` в settings.json?** → Опускаем ⇒ срабатывание
  на всех `source` (§353). Значения matcher (`startup`/…/`fork`) сверены по
  докам.
- **Q (scope): статуслайн/PreCompact в тот же settings.json сейчас?** → Нет,
  это T054/T055; T052 кладёт только SessionStart-блок (scope discipline).

## Analyze (заполняется Claude)

Чистый проход. Issues:

- 🟢 **Note.** `dt/sessions.py` делает FS-запись — это не нарушает
  «чистое ядро»: инвариант репо — typer-free и git-free, FS ядру разрешён
  (`tasks.py` пишет файлы задач). Атомарность через temp+`os.replace` в том
  же каталоге `sessions/`.
- 🟢 **Note.** `context_cli._emit_hook` уже ловит всё в `except Exception →
  Exit(0)`. Запись реестра встраивается **после** формирования `additional`
  и оборачивается собственным глотающим `try`, чтобы её провал не отменял
  уже готовый payload (payload печатается всегда, если ошибка не случилась
  раньше него).
- 🟢 **Note.** cwd для git-фактов ≠ cwd в реестре концептуально, но на
  практике совпадают (хук исполняется в cwd сессии). Записываем именно
  stdin-`cwd` — это то, что нужно `dt resume` для `cd`.
- 🟢 **Note.** `_templates_suffix: ""` рендерит settings.json как Jinja;
  `{{ }}` в файле нет, JSON проходит дословно. Проверяется smoke-тестом
  `dreamteam init`.
- 🟢 **Note.** Coverage: `dt/sessions.py` покрывается юнит-тестами (build /
  write / read round-trip / overwrite / атомарность), путь хука — CLI-тестами
  с подставленным stdin.
