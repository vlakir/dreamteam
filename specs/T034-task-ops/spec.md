## 1. Overview

Вторая задача эпика E1 и второй шаг критического пути
`T033 → T034 → T051 → T052 → T053`. Поверх библиотечного фундамента T033
вводит **первые пользовательские команды** оперативного слоя — базовый
жизненный цикл записи задачи:

- `dt task new "<title>" [--deps …] [--blocks …] [--parent T0NN] [--json]`
- `dt task show T0NN [--json]`
- `dt task move T0NN <status>`
- `dt task split T0NN "<title>"`

Задача поставляет: (1) атомарную выдачу ID через файл-счётчик `counter` +
`O_EXCL` на файле записи; (2) чистый слой операций в `dt/tasks.py`
(typer-free); (3) тонкие Typer-обёртки — под-приложение `task`,
подключённое к общему `app` (доступно и как `dt task …`, и как
`dreamteam task …`).

**Явно НЕ в этой задаче** (каждое — своя задача): `find` (T038),
`start` (T039), `check`/`ready` (T035), `board` (T037), `backlog sync`
(T040), `state export/import` (T041), `migrate` (T042), `worktree …` (T036).

## 2. Сценарии использования

- **Заведение задачи.** Агент/человек: `dt task new "Изменить вид курсора"
  --deps T033`. Команда выделяет следующий свободный ID, создаёт запись
  `T<NNN>.md` в статусе `todo`, проставляет `created`/`updated` = сегодня.
- **Побочная задача** (E9.2). `dt task new "…" --parent T034` — рождается
  задача-ребёнок из обсуждения T034; сессия и ветка не меняются.
- **Блокирующее открытие** (E9.2). `dt task new "…" --blocks T034` — новая
  задача блокирует T034: T034 получает новую в свой `deps` и уходит из
  будущего `dt task ready` (T035).
- **Расщепление** (E9.2). `dt task split T034 "вторая половина"` — создаётся
  задача с `parent: T034`. Сужение scope самой T034 фиксирует агент в теле
  записи вручную (не автоматизируется — см. Clarify).
- **Смена статуса.** `dt task move T034 review` — статус → `review`,
  `updated` → сегодня.
- **Просмотр.** `dt task show T034` — человекочитаемый вывод; `--json` —
  полная запись для агента.

## 3. Functional Requirements

**Выдача ID (`counter` + `O_EXCL`):**

- ДОЛЖНА: хранить счётчик в единственном файле `$DT_STORE/counter`
  (целое — последний выданный номер; отсутствие файла = 0).
- ДОЛЖНА: выделять номер атомарно — кандидат `counter+1`, попытка создать
  `tasks/T<NNN>.md` с `O_EXCL`; при `FileExistsError` — инкремент и повтор
  (пропуск уже занятых номеров). Файл записи — арбитр гонки: два параллельных
  worktree не могут получить один номер по построению.
- ДОЛЖНА: после резервирования обновлять `counter` до нового максимума.
- ДОЛЖНА: форматировать ID как `T` + номер, дополненный нулями минимум до
  3 цифр (`T001`, `T034`, естественное расширение для `T1000`).

**`dt task new`:**

- ДОЛЖНА: **сначала** валидировать все ссылки (`--deps`, `--parent`,
  `--blocks`) — каждый ID должен существовать в store; при отсутствии —
  внятная ошибка и **ничего не создаётся** (валидация до выделения ID,
  чтобы не оставлять «дыру» в нумерации).
- ДОЛЖНА: создавать запись в статусе `todo`, `deps` = переданные `--deps`,
  `parent` = `--parent`, `created`/`updated` = сегодня, тело пустое.
- ДОЛЖНА: для каждого `--blocks B` дописывать новый ID в `B.deps` (если
  ещё нет) и обновлять `B.updated` = сегодня.
- ДОЛЖНА: принимать `--deps`/`--blocks` как повторяемые опции И как
  список через запятую (`--deps T003,T005` ≡ `--deps T003 --deps T005`).
- МОЖЕТ: `--json` — печатать созданную запись целиком (см. контракт ниже).

**`dt task show`:**

- ДОЛЖНА: загружать запись по ID; при отсутствии — внятная ошибка, код ≠ 0.
- ДОЛЖНА: без `--json` — человекочитаемый вывод (ID, статус, заголовок,
  поля, тело); с `--json` — полная запись.

**`dt task move`:**

- ДОЛЖНА: менять `status` на переданный (валидный ∈ `{todo, doing, review,
  done, dropped}`), обновлять `updated` = сегодня.
- ДОЛЖНА: при неизвестном статусе — ошибка со списком допустимых значений.
- НЕ ДОЛЖНА: навязывать граф допустимых переходов (любой валидный статус
  разрешён; переходы — забота методики, не инструмента).

**`dt task split`:**

- ДОЛЖНА: валидировать существование родителя; создавать **новую** задачу
  с `parent: <родитель>` (эквивалент `new` с `--parent`), статус `todo`.
- НЕ ДОЛЖНА: править запись родителя (сужение scope фиксирует агент вручную).

**Контракт `--json`** (единый для `new`/`show`/`split`; агент-facing):

- Полная запись задачи в JSON: все поля frontmatter (`id`, `title`,
  `status`, `deps`, `parent`, `spec`, `branch`, `pr`, `tags`, `created`,
  `updated`) + `body`. Даты — ISO-строки. Одна стабильная форма во всех
  командах.

**Слой и подключение:**

- ДОЛЖНА: чистые операции жить в `src/dreamteam/dt/tasks.py` (typer-free,
  как весь `dt/`); Typer-обёртки — вне `dt/`.
- ДОЛЖНА: под-приложение `task` подключаться к общему `app` — команды
  доступны как `dt task …` и `dreamteam task …`.
- ДОЛЖНА: ошибки операций (`TaskError`, `DtHomeError`) на уровне CLI
  маппиться в stderr + код возврата ≠ 0, без трассировки.

## 4. Success Criteria

- Два подряд `dt task new` дают `T001`, `T002` в пустом store; повторный
  запуск после ручного создания `T002.md` пропускает занятый номер.
- `dt task new --blocks T001` дописывает новый ID в `T001.deps` и обновляет
  `T001.updated`.
- `dt task new --deps T999` (несуществующий) — ошибка, код ≠ 0, запись не
  создана, `counter` не сдвинут.
- `dt task move T001 review` меняет статус и `updated`; `dt task move T001
  bogus` — ошибка со списком статусов.
- `dt task split T001 "…"` создаёт запись с `parent: T001`, родитель не
  изменён.
- `--json` любой команды — валидный JSON с полной записью (даты ISO).
- Coverage нового кода `src/dreamteam/dt/tasks.py` и CLI-обёрток ≥ 80%.

## 5. Key Entities

- **`counter`** — файл `$DT_STORE/counter`, целое: последний выданный номер.
  Высокий water-mark; арбитр атомарности — `O_EXCL` на файле записи.
- **`TaskError`** — исключение операций слоя задач (не найдена, битая
  ссылка, невалидный статус). Отделено от `DtHomeError` (резолв store).
- **`task` Typer-app** — под-приложение CLI с командами `new/show/move/
  split`, точка роста для будущих `dt task` подкоманд (T035, T038, T039).

## 6. Assumptions & Constraints

- Хранилище одно на репозиторий (worktree-независимость T033) — `O_EXCL` на
  файле записи достаточен как арбитр даже при параллельных worktree.
- `datetime.date.today()` — источник «сегодня»; чистые функции принимают
  `today` параметром (детерминизм в тестах), CLI подставляет `date.today()`.
- Для команд T034 git не обязателен: они опираются на `store_dir()`
  (`$DT_HOME/store`); при `DT_HOME`-override резолв не вызывает git.
  `worktree_slug`/git нужны только `start`/`context` (T039/T051).
- Запись мутаций (`move`, `--blocks`-цель) — обычный `save_task` (torn-write
  маловероятен: писатель на задачу один). Полный atomic-rename — возможный
  follow-up, вне scope.
- Новых runtime-зависимостей нет (pydantic/typer/pyyaml уже есть).

## 7. Out of Scope

- `dt task find` (T038), `start` (T039), `check`/`ready` (T035).
- `dt board` (T037), `backlog sync` (T040), `state export/import` (T041).
- `dt migrate tasks` (T042), `dt worktree …` (T036).
- Запись `current-task` / `context.line` — `start` (T039) / `move`-хук (T051+).
- Реестр сессий, tmux, statusline — T052/T054.
- Сидирование `counter` из существующих markdown-T-ID репозитория dreamteam —
  это делает `migrate` (T042); до тех пор `dt task new` на самом dreamteam не
  используется «по-настоящему», T034 обкатывается на изолированных временных
  store.

## Clarify (заполняется Claude)

### Resolved (с ответами)

- **Q (битые ссылки `--deps`/`--parent`/`--blocks`):** → **Hard error.**
  Store — единственный источник истины; опечатки ловятся сразу, `--parent`/
  `--blocks` всё равно требуют загрузки цели. Валидация до выделения ID.
- **Q (контракт `--json`):** → **полная запись задачи** в JSON, одна
  стабильная форма для `new`/`show`/`split`.
- **Q (глубина `split`):** → **только ребёнок** (`parent:` проставлен);
  правку тела родителя (сужение scope) делает агент — дизайн прямо говорит,
  что сужение фиксируется в теле методикой, не автоматикой.
- **Q (module layout):** Typer-обёртки — отдельный модуль
  `src/dreamteam/task_cli.py`, подключается в `cli.py` через
  `app.add_typer(task_app, name='task')`. `dt/` остаётся typer-free; `cli.py`
  не разрастается операционными командами. Точка роста для T035+.
- **Q (механика `O_EXCL`):** арбитр гонки — `os.open(..., O_CREAT|O_EXCL)` на
  файле записи; `counter` — стартовая подсказка/water-mark, не источник
  истины. Слегка устаревший `counter` вызывает лишь до-скан, не коллизию.
- **Q (парсинг `--deps`/`--blocks`):** повторяемая опция + split по запятым
  (оба стиля), нормализация: flatten → split ',' → strip → отбросить пустые.
- **Q (валидация статуса в `move`):** `TASK_STATUSES = get_args(TaskStatus)`
  в `model.py` — единственный источник; CLI-enum и проверка ссылаются на
  него, тест на согласованность против дрейфа.
- **Q (источник «сегодня»):** `date.today()` в CLI, проброс `today` в чистые
  функции для детерминизма тестов.

### Open questions

- нет (развилки закрыты до реализации).

## Analyze (заполняется Claude)

- 🟢 **Note.** Валидация ссылок до выделения ID — важный порядок: иначе
  битый `--blocks` оставил бы зарезервированный, но недописанный номер
  («дыру»). Тест фиксирует: битая ссылка → `counter` не сдвинут.
- 🟡 **Warning → resolved.** `--blocks` мутирует **чужую** запись (цель
  получает dep). Это единственная в T034 операция, меняющая не-свою задачу;
  дизайн E9.2 её прямо предписывает. `updated` цели обновляется (запись
  реально изменена). Идемпотентность: повторный `--blocks` не дублирует ID
  в `deps`.
- 🟡 **Warning → resolved.** `O_EXCL`-цикл и `counter`: при гонке двух
  worktree оба стартуют от одного `counter`, но `O_EXCL` отдаёт номер лишь
  одному; проигравший инкрементит и берёт следующий. `counter` пишется как
  `max(текущий_на_диске, кандидат)` — откат назад невозможен.
- 🟢 **Note.** Коллизия с markdown-T-ID самого dreamteam (пустой store →
  `T001`) — ожидаема и осознана: реконсиляция — `migrate` (T042, точка
  невозврата). T034 обкатывается на временных store; запись задачи T034
  по-прежнему ведётся в markdown.
- 🟢 **Note.** `TaskError` отделён от `DtHomeError`: разные слои (операции
  над записями vs резолв корня). CLI ловит оба, маппит в код ≠ 0 без
  трассировки — как остальной `dt`.
- 🟢 **Note.** `task_cli.py` не импортирует `cli.py` (только `dt/*`) — цикла
  импорта нет; `cli.py` импортирует `task_app` из `task_cli`.
- 🟡 **Warning → resolved (ревью qodo, PR #80).** `_record_path` строил путь
  из сырого `task_id` — крафтовый ID (`../../repo/.git/x`) уводил `show`/`move`
  за `store/tasks/` (path traversal, нарушение инварианта «не внутри git»).
  Введён валидатор `^T\d{3,}$` (`_ensure_valid_id`), вызывается на всех входных
  ID (`load_existing`, `_require_exists` для deps/blocks/parent, `split`) до
  любого обращения к ФС. Тесты на `../x`, `T001/../x`, lowercase и т.п.
- 🟢 **Note (ревью qodo).** Файловые сбои (`OSError` при записи записи/счётчика)
  минуют `TaskError` → CLI `_run` дополнительно ловит `OSError` и маппит в код
  ≠ 0 без трассировки. Отрицательный `counter` теперь считается битым.
- Проход чистый: критических противоречий нет, реализация разблокирована.
