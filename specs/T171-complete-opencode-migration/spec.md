# T171: Завершение миграции проектов на OpenCode

**Статус:** согласованный контракт; реализация и приёмка не выполнены.
**Дата:** 2026-10-16. **База раунда:**
`e32fbe14179588eaa8c8c75d8b61d69809baf758` (после T170).
**Источники:** AGENTS.md, ADR OpenCode от 2026-10-15, T170 spec/acceptance,
явные решения Разработчика, зафиксированные в clarify.md.
Корневого CONCEPT.md в репозитории нет; новый исходный замысел не создаём.

## Цель и scope

Завершить безопасный автоматический перенос выбранного проекта с Claude Code
на OpenCode через `dt update` и `dt apply` unmanaged-проекта, затем выпустить
stable 2.0.0 только после проверок. Не сканировать все проекты при установке
пакета, не мигрировать реальные оригиналы, не создавать generic migration
framework и не менять обычную политику merge conflicts вне миграции.

## Обязательные требования

### R1. Предварительно работающий OpenCode

На хосте, где выполняется миграция, обязателен установленный и фактически
запускаемый совместимый OpenCode. Для T171 поддерживаемая версия — **1.19.0**:
именно она закреплена и испытана в T170; произвольное `>=1.19.0` не доказывает
совместимости будущих релизов. Ensemble остаётся 0.18.0; миграционный preflight
не запускает сервер/плагин и не требует его регистрации, сети или авторизации.

Проверить найденный в PATH executable отдельным subprocess без shell через
`opencode --version`, с конечным timeout (техническая константа 5 секунд),
проверить exit status и строго разбираемую версию. Проверка выполняется из
безопасного существующего служебного cwd, не целевого проекта. Не вызывать
login, модели, API, MCP и не устанавливать ничего автоматически. Отсутствие,
неисполняемость, сбой, timeout, непонятная/неподдерживаемая версия — понятная
ошибка без изменений проекта, backup, journal, deletes и answers. Проверка
предшествует также интерактивным ответам миграции. `--force` её не обходит.
Если применение отделено от планирования паузой/подтверждением, проверка
повторяется непосредственно перед первой записью. Dry-run также остаётся
локальным и read-only. Обычный init создаёт только OpenCode-артефакты;
новую обязательную migration-проверку для чистого init не вводим.

### R2. Полная read-only классификация до изменений

Обрабатывать только явно выбранный root. Учесть legacy-only, destination-only,
BOTH (CLAUDE.md + AGENTS.md и пары .claude/.opencode), неизменённые/изменённые
managed-файлы, полезные проектные правила, роли и custom-файлы. У update
проверяемая bundle/base служит основанием merge; отсутствие базы не допускает
потери данных даже с force. У unmanaged apply нет выдуманной Copier-базы:
сохранить исходное содержимое и проверить перенос явно. Наличие destination
не означает, что legacy можно игнорировать или уничтожить.

Описать конкретный allowlist поддерживаемых артефактов и преобразований в коде
и пользовательской документации. Неизвестный активный параметр, непереносимый
hook, неразбираемый config или неоднозначное преобразование блокирует всю
миграцию до записи. Отчёт называет путь/категорию/действие для исправления,
не печатает значения. Нельзя молча терять permission, hook или роль, считать
их перенесёнными по факту копирования байтов либо отключать ради успеха.

`.git`, `.claude/worktrees` и их содержимое исключены из обхода и удаления;
внешние symlink не разыменовывать, не менять и не удалять. Если неперенесённые
или исключённые данные остаются, родительскую .claude не удалять рекурсивно.
Пути, необходимые для переноса, через symlink — блокер, не повод пройти ссылку.

### R2a. Минимальный поддерживаемый mapping

Verified 1.7.0 recipe: `.claude/agents/architect.md` с `name=architect`,
`tools: Read, Glob, Grep` и original model answer заменяется новым rendered
read-only architect. Base render строить с **оригинальными** answers до alias
normalization; inherit означает отсутствие model, opus/sonnet/haiku → inherit
только по T170 правилу, без выбора провайдера. Неизвестные keys или изменённые
name/tools/model — BLOCK. User description/body edits при неизменных control
fields сохранять three-way; conflicts BLOCK без markers. `CLAUDE.md` и
`.claude/team-roles.md` — verified-base three-way с проверкой useful deltas.
В 1.7.0 нет settings/commands/skills/hooks под .claude: baseline exceptions
для них не выдумывать. Backend подтвердил recipe чтением точного bundle tag;
tester покрывает его независимо.
Исторические теги 1.5/1.6 не удаляются. Применимость recipe к иной базе
проверяется по exact shapes; обещания автоматической совместимости всех старых
версий нет, неизвестная форма безопасно блокирует до mutation.

Для managed update сначала различать проверенный bundled baseline и custom:
неизменённая известная template plumbing (включая старые model/tools/settings)
заменяется проверенным новым template counterpart, а полезные text edits
сохраняются three-way. Нельзя применять ограничения custom ниже вслепую к
каждому baseline artifact и блокировать чистый 1.7.0 → 2.0.0. Неизвестные
custom поля/изменённая executable семантика блокируют; исторический snapshot
служит доказательством происхождения, но не поводом молча трактовать custom.

- `CLAUDE.md` → `AGENTS.md`: нейтральные проектные правила сохраняются;
  известные bundled template части преобразуются проверяемым template merge.
  Неизвестные активные инструкции запуска Claude CLI не считаются переносом:
  блокировать, а не приклеивать старый текст к новым правилам.
- `.claude/agents/*.md` → `.opencode/agents/*.md`, `.claude/commands/*.md` →
  `.opencode/commands/*.md`, `.claude/skills/<name>/SKILL.md` → соответствующий
  `.opencode/skills/<name>/SKILL.md`: минимально поддерживается нейтральный
  markdown без исполняемой legacy-семантики. Для custom frontmatter допускаются
  только строковые `name` и `description` (name согласован с именем артефакта).
  Это нейтральные metadata, не перевод control-полей. Неизвестные поля, model,
  tools, permissions, hooks — BLOCK, не drop и не guessed rewrite. Если body
  содержит неизвестную active CLI семантику, нейтральная metadata её не разрешает.
- Settings: минимально поддерживается пустой JSON object; любой непустой или
  неизвестный key, включая settings.local, блокирует до mutation. Не заявлять
  поддержку личных MCP/permissions/auth по одному успешному копированию.
- BOTH: одинаковые результаты объединяются без дубликатов; непересекающиеся
  additions сохраняются; семантически неоднозначные/overlapping изменения —
  conflict 2 без записи. Destination не побеждает автоматически.
- `.claude/skills` автоматически сканируется OpenCode и не является безопасным
  архивом. Supported skills переносить, неизвестные — BLOCK. Архивные snapshots
  bundle/provenance не являются активным config и не переписываются.

Точный parser/allowlist документируется backend, но не может ослабить этот
минимум или молча расширить claims. Диагностика version probe не печатает
сырой stdout/stderr потенциально чувствительного CLI; только safe category.

### R3. Сохранность и проверяемое завершение

До первой записи создать минимальный защищённый recovery snapshot/journal
**вне project git tree и вне активного legacy namespace**. Не копировать весь
проект. Сохранить затрагиваемые оригиналы, отсутствие ранее новых файлов,
достаточные fingerprints и этапы операции. Каталог доступен только владельцу
(0700, файлы 0600), не попадает в git/дистрибутив/обычные отчёты.
`settings.local` и иные секретные данные не выводятся в diff/log и не входят
в git backup. Если безопасное преобразование неизвестно — блокировать до
создания snapshot, источник оставить. Безопасно поддержанный секретный файл
может храниться только в таком приватном recovery, не в новом публичном config.

Сначала подготовить результат и проверить сохранение полезных данных обеих
сторон, затем безопасно применить изменения и проверить фактические файлы.
Удалять конкретный legacy-источник можно только после verified transfer;
наличие backup само по себе не является verified transfer. При конфликте
не изменять проект и не продвигать answers; вернуть 2 и безопасный отчёт.
Unsupported/prerequisite/path/I/O ошибки — 1, полный verified успех — 0.
Никакого success или продвижения migration/base metadata при partial result.
`.copier-answers.yml` и признак completion фиксируются последними, как часть
восстанавливаемой операции; apply не делает проект managed при неуспехе.

Гарантия — сохранность и проверяемое восстановление, не атомарность всех
файлов каталога. На ошибке восстановить исходное состояние, если это безопасно;
при прерывании/неполном rollback сохранить journal и дать конкретный путь
восстановления. Перед повтором сверить journal с filesystem: сбой между записью
и обновлением journal не означает, что запись не выполнена. Если после сбоя
файлы изменил пользователь, не затереть их автоматическим rollback: остановиться
с сохранением всех версий. После завершения повторная миграция — no-op.
Удалять recovery автоматически для объявления успеха не требуется.

### R4. Совместимость публичной поставки

`dt update` автоматически выбирает миграционный путь при legacy, включая BOTH;
unmanaged `dt apply` делает то же. Его keep/overwrite/save-as-new и update
`--force` не отменяют R1–R3. Не расширять эти ограничения на обычные unrelated
template conflicts. Установка/обновление wheel не ищет проекты на диске.

Активные инструкции/шаблоны/подсказки больше не требуют Claude CLI, Max или
Codex CLI. Anthropic API остаётся поддерживаемым провайдером OpenCode;
модели/провайдеры — личная конфигурация. Не удалять исторические bundle/git
tags, старые ADR и provenance: они нужны для merge и понимания решений.

## Проверки и результаты

### Уточнение платформы приёмки и native question (2026-10-16)

Разработчик явно подтвердил: полных release gates на **Linux достаточно**
для T171 stable 2.0.0. Secure legacy migration/recovery на Windows не реализована
и не протестирована; там требуется ранний controlled unsupported без project
или recovery writes. Этот отказ не распространяется на обычный native OpenCode
CLI без legacy/pending migration. Это граница поставки, не ослабление Linux
гейтов и не заявление Windows-поддержки.

В репозитории и rendered template роль tech-lead явно разрешает только native
`permission.question: allow`: custom primary agents OpenCode 1.19.0 иначе
наследуют `question: deny`. Specialist roles не получают это разрешение;
прочие права, модели/провайдеры и личные конфиги не меняются. Новые MCP/plugins
не нужны. Static/render tests не доказывают фактический UI-опрос: его проверка
после безопасного перезапуска активной команды остаётся отдельным smoke.

Матрица — acceptance.md, выполнение и ownership — plan.md, риски — analysis.md.
Одна репетиция обязательна на изолированной копии реального проекта, без
изменения оригинала или использования действующих секретов. Stable 2.0.0
допустим только после полного набора гейтов, независимого review и принятой
репетиции. Документы этого раунда — база исполнения, не доказательство успеха.
