## 1. Overview

Третья задача эпика E1 и продолжение критического пути
`T033 → T034 → T051 → T052 → T053` (сама T035 — точка входа с уже
выполненной `deps: T034`, не на самом критическом пути). Поверх операций
T034 вводит **валидацию целостности** и **вопрос «что можно брать»**:

- `dt task check [--json]` — целостность графа задач.
- `dt task ready [--json]` — задачи `todo`, у которых все `deps` в `done`.

Плюс подключение `check` в CI/pre-push по образцу `scripts/translate_check.py`
(критерий приёмки 5) и свёртка запаркованного микронита валидатора ID
(`\d` → `[0-9]`, микро-нит из ревью T034).

**Явно НЕ в этой задаче** (каждое — своя задача): `dt worktree …` (T036),
`dt board` (T037), `dt task find` (T038), `dt task start` (T039),
`dt backlog sync` (T040), `dt migrate tasks` (T042), `dt context` (T051).

## 2. Сценарии использования

- **Проверка перед push.** CI-шаг `dt task check` падает, если в store
  появился цикл `deps`, битая ссылка `deps`/`parent` или (на ветке своей
  задачи) пропал файл спеки. На пустом store — проходит vacuously.
- **«Что дальше».** Агент: `dt task ready --json` — список задач `todo`,
  все `deps` которых уже `done`; достаточный машинный ответ на «что можно
  брать в работу прямо сейчас» (критерий приёмки 4).
- **Ручная валидация.** Человек после правки записей руками:
  `dt task check` — список ошибок и предупреждений, код ≠ 0 при ошибках.

## 3. Functional Requirements

**`dt task check`:**

- ДОЛЖНА: загружать **все** записи `$DT_STORE/tasks/T*.md` в граф.
- ДОЛЖНА (ERROR): сообщать о ссылке `deps`/`parent` на несуществующий ID.
- ДОЛЖНА (ERROR): обнаруживать циклы в графе `deps` (ребро «задача → её
  `deps`») и печатать цикл. Самозависимость (`T005` в своих `deps`) — цикл.
- ДОЛЖНА (WARNING / ERROR): для записи с непустым `spec` — резолвить путь
  относительно корня **текущей рабочей копии** (`git rev-parse
  --show-toplevel`). Файла нет → **WARNING**; но если `branch` записи задан
  и совпадает с **текущей выгруженной веткой** (`git rev-parse --abbrev-ref
  HEAD`) — **ERROR** (спека обязана быть здесь, а её нет).
- ДОЛЖНА: код возврата ≠ 0 при наличии хотя бы одной ошибки; при только-
  предупреждениях — код 0. Ошибки — в stderr; итоговая сводка — одна строка.
- МОЖЕТ: `--json` — `{"errors": [...], "warnings": [...]}`, каждый элемент
  `{task, kind, message}`; код возврата тот же.
- ЗАМЕЧАНИЕ: поле `blocks` в записи не хранится (T034 транслирует `--blocks`
  в `deps` цели), поэтому «целостность `blocks`» из дизайна покрывается
  проверкой `deps` — отдельной ветки для `blocks` нет.

**`dt task ready`:**

- ДОЛЖНА: возвращать задачи `status == todo`, у которых **все** `deps`
  существуют и имеют `status == done`. Задача без `deps` — готова.
- НЕ ДОЛЖНА: считать готовой задачу с несуществующим `deps` (её ловит
  `check`); такая просто не попадает в `ready`.
- ДОЛЖНА: стабильный порядок по ID.
- ДОЛЖНА: без `--json` — по строке на задачу (`ID  title`); пусто → одна
  информационная строка. С `--json` — список **полных записей** (контракт
  `--json` из T034).

**Слой и git-осведомлённость:**

- ДОЛЖНА: чистые операции (`check_tasks`, `ready_tasks`, загрузка графа)
  жить в `src/dreamteam/dt/tasks.py` (typer-free). `check_tasks` принимает
  git-контекст (`repo_root`, `current_branch`) **параметрами** — прямых
  git-вызовов в `tasks.py` нет.
- ДОЛЖНА: git-контекст добывать в `dt/paths.py` (git-осведомлённый модуль):
  helpers `repo_toplevel()` и `current_branch()`. CLI подставляет их в
  `check_tasks`; тесты передают значения напрямую (детерминизм).
- ДОЛЖНА: Typer-обёртки `check`/`ready` — в `task_cli.py`, к тому же
  под-приложению `task`.

**Подключение в pre-push (критерий приёмки 5):**

- ДОЛЖНА: шаг `uv run dt task check` в `.github/workflows/ci.yml` рядом с
  translate-check. Отдельный wrapper-скрипт не вводим — команда сама есть
  проверка.
- ДОЛЖНА: строка про `dt task check` в pre-push разделе проектного
  `CLAUDE.md` (с оговоркой «пока проходит vacuously, осмысленно после
  догфудинга T042»).

**Микро-нит из ревью T034:**

- ДОЛЖНА: `_ID_RE` = `^T[0-9]{3,}$` (ASCII-цифры вместо `\d`), чтобы
  unicode-цифры (`T۰۰۱`) не давали валидный-но-странный filename. Это не
  security-фикс (path-traversal уже закрыт), а робастность. Тест на
  unicode-digit вход → invalid.

## 4. Success Criteria

- Чистый store из связных задач: `check` → код 0, «ok».
- Цикл `T001↔T002` (взаимные `deps`) → `check` печатает цикл, код ≠ 0.
- Запись с `deps: [T999]` (нет такой) → ERROR, код ≠ 0.
- Запись с `parent: T999` (нет такой) → ERROR, код ≠ 0.
- Запись с `spec: specs/x/spec.md`, файла нет, `branch` не совпадает с
  текущей → WARNING, код 0. То же, но `branch == current_branch` → ERROR,
  код ≠ 0.
- `ready`: `T001 done`, `T002 todo deps:[T001]` → `T002` готова; если
  `T001` не `done` → `T002` не готова; `T003 todo` без `deps` → готова.
- `dt task show 'T۰۰۱'` (unicode-цифры) → invalid, код ≠ 0.
- Coverage нового кода в `dt/tasks.py` и CLI-обёрток ≥ 80%.

## 5. Key Entities

- **`CheckIssue`** — `(task_id, kind, message)`, где `kind ∈ {error,
  warning}`. Плоский результат `check_tasks` → `CheckReport`
  (`errors`/`warnings`).
- **`check_tasks(store, *, repo_root=None, current_branch=None)`** — чистая
  функция; без `repo_root` spec-проверка **пропускается** (путь не резолвить);
  при известном `repo_root`, но без `current_branch` (detached HEAD) —
  отсутствие файла всегда WARNING, без эскалации. spec-путь обязан быть
  repo-relative: absolute / escaping (`..`) отвергается как «не найден»
  (иначе внешний файл замаскировал бы пропажу — false-negative гейта).
- **`ready_tasks(store) -> list[Task]`** — чистая функция над графом.
- **`load_all_tasks(store) -> dict[str, Task]`** — загрузка всех записей
  (переиспользуется `check` и `ready`; позже — `board` T037).

## 6. Assumptions & Constraints

- Граф маленький (задачи проекта, десятки-сотни) — DFS-обход циклов без
  оптимизаций достаточен.
- spec-путь резолвится относительно **текущей** рабочей копии, не main:
  проверка про «выгружена ли ветка задачи» — про файлы текущего worktree.
- Записи уже прошли pydantic-валидацию при загрузке (`load_task`);
  `check` не пере-валидирует схему frontmatter — только граф и spec-файлы.
- Новых runtime-зависимостей нет.
- На самом dreamteam store пуст до `migrate` (T042) — `check` в CI проходит
  vacuously; это ожидаемо и есть догфудинг-хук.

## 7. Out of Scope

- `dt worktree …` (T036), `dt board` (T037), `dt task find` (T038),
  `dt task start` (T039), `dt backlog sync` (T040), `migrate` (T042),
  `dt context` (T051).
- Валидация схемы frontmatter записей (это делает pydantic при загрузке).
- Проверка существования spec-файла на **других** ветках через git
  (design говорит «выгружена» = текущая рабочая копия; кросс-branch обход
  не делаем).
- Жёсткая проверка расхождения BACKLOG.md в pre-push (дизайн E1 прямо
  против — это мягкая строка `dt context`, T051).

## Analyze (заполняется Claude)

- 🟢 **Note.** spec-проверка резолвит путь относительно **текущей** рабочей
  копии (`show-toplevel`), не main-worktree: смысл эскалации — «ты на ветке
  задачи, спека обязана быть в этих файлах, а её нет». На чужой ветке файла
  законно может не быть → WARNING.
- 🟢 **Note.** Без `repo_root` (не-git вызовы, хуки) spec-проверка
  пропускается — путь не резолвится, complaining было бы шумом. При известном
  `repo_root`, но detached HEAD (`current_branch is None`) отсутствие файла —
  WARNING без эскалации. Детерминировано для юнит-тестов.
- 🟡 **Warning → resolved (ревью qodo, PR #81).** spec-путь резолвился как
  `repo_root / task.spec` без проверки — absolute-путь молча ронял `repo_root`,
  `..` уводил наружу: внешний существующий файл гасил бы WARNING/ERROR
  (false-negative CI-гейта). Введён `_spec_present`: отвергает absolute и
  escaping пути и требует `is_file()` внутри `repo_root`. Тесты на оба вектора.
- 🟢 **Note (ревью qodo, PR #81).** Тест-хелпер `_write` типизирован
  `status: TaskStatus` (не `str`) — снят `# type: ignore[arg-type]`, чинили
  тип, а не глушили (правило «никаких suppressions без обсуждения»).
- 🟡 **Warning → resolved.** `ready` не должна падать на битом `deps`:
  несуществующий dep не делает задачу «готовой» (не можем подтвердить
  `done`), но и не роняет команду — это работа `check`. Тест фиксирует.
- 🟢 **Note.** `load_all_tasks` — общий загрузчик графа для `check`/`ready`
  (и позже `board` T037); фильтрует по валидному `T[0-9]{3,}.md`, мусорные
  имена в `tasks/` игнорируются, не роняя обход.
- 🟡 **Warning → resolved.** Цикл-детект: ребро «задача → dep». Самоссылка
  (`T005.deps ⊇ [T005]`) — цикл длины 1. DFS с тремя цветами; при находке —
  печать пути цикла, дальнейший обход не прерывается (собираем все проблемы).
- 🟢 **Note.** `check` exit-code: ошибки — данные (не исключения), поэтому
  CLI после отчёта сам делает `typer.Exit(1)` при `errors`; `_run` T034
  маппит лишь `TaskError`/`DtHomeError`/`OSError` — для `check`/`ready`
  нужен runner, возвращающий произвольный тип (обобщаем `_run`).
- Проход чистый: критических противоречий нет, реализация разблокирована.
