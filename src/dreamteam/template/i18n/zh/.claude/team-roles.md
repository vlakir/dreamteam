# 团队角色：架构师与设计师

本项目在方法论之上自带一套可复用的协作机制。**主导会话**（本 Claude Code
会话）负责编排；**人**（开发者）拍板。两个角色默认可用——在某个具体任务里用不
用它们，由主导会话临场决定，而不是创建项目时勾选的选项。

角色的真理之源与「记忆」是项目自身的方法论文件（`CONCEPT.md`、`DECISIONS.md`、
`specs/`、`BOARD.md`/`BACKLOG.md`），而不是外部存储。并不禁止主导会话使用外部
记忆，但它只是文件里正典的镜像：被清空了也不丢东西——一切都能从项目里恢复。

> **`dreamteam update` 之后的生效时机。**这些角色（架构师子代理与本方法论的导入）
> 在 Claude Code **会话启动时**才被加载，而不是在更新的那一刻。如果你是在活动会话
> 里跑的 `update`，重启会话，让主导会话看到新角色。

## 主导会话（Lead）

项目里的主 Claude Code 会话（就是本会话）。它不是单独的产物，而是由
`CLAUDE.md` 驱动的行为。写生产代码、推进任务、调用架构师和设计师，并整合它们
的结果。角色之间没有实时的三方聊天：主导会话分别与每个角色交流，再自己把回答
合并起来。

## 架构师（只读子代理）

关于逻辑与架构决策的顾问。以子代理 `.claude/agents/architect.md` 的形式存在；
Claude Code 会自动发现它——无需为它单独 import。只读（Read/Glob/Grep）：它读
方法论文件、推理、给出建议——但从不提交，也不写代码。

**何时调用：**选择方案、剖析某个技术决策、评审架构、心里那点「这会不会反过来坑
我们」的疑虑。不用于写代码（那是主导会话的事），也不用于视觉（那是设计师的事）。

**如何调用：**把问题连同上下文委派给 `architect` 子代理——它会自己去读所需的方
法论文件。例如：「问架构师：X 是否该拆成单独的模块？给出上下文、带权衡的选项和
建议。」

**它返回什么：**一份「背景 → 带权衡的选项 → 建议 → 开放的分岔」形式的分析，并
标明依据了哪些方法论文件。当决定成熟时，它会按项目的格式为 `DECISIONS.md` 提议
一条现成的 ADR-Lite 记录。

**「提议 → 由人拍板 → ADR」的循环：**

1. 架构师提议一个决定和一份 ADR 草稿。
2. 由人拍板——架构师是只读的，不替人做决定。
3. 主导会话/人把最终记录写入 `DECISIONS.md`。

这样，重要的决定就沉淀进项目文件里，而不是留在代理易失的记忆里。

## 设计师（通过 MCP 的 Claude Design）

用于视觉工作的外部 Claude Design 代理：界面、原型、视觉规范。主导会话把它作为
MCP 直接调用，不把它包成子代理。

**前置条件——账户层面的一次性设置：**

1. `claude mcp add --scope user --transport http claude-design https://api.anthropic.com/v1/design/mcp`
2. `/design-login`——OAuth 认证（真正把它连上的是这一步，而不是 `add`）。
3. （可选）`claude mcp list`——确认服务器已注册。

Claude Design 的访问权在 Pro / Max / Team / Enterprise 套餐上（beta）。如果 MCP
没连上或不可用，这**不是错误，而是一个分岔**：主导会话要么把设计师连上，要么不
用它继续干。若账户配置了 design system（品牌色、字体排印），设计会采用它；对于
全新的个人项目，则用 Claude Design 的默认值。

**何时调用：**你需要视觉设计或界面原型。主导会话把
`specs/design-brief-template.md` 里的简报交给设计师，迭代，并把结果作为原型拉进
仓库。

**重要：**设计师产出的是 **web**（HTML/CSS/JS），而不是项目的目标技术栈。它的产
物是一份视觉规范；把它转译到目标 UI 技术栈始终是主导会话单独的一步。

## 诚实的局限

- 没有实时的三方对话：架构师和设计师是可调用的角色，而不是共享聊天里平等的对话
  者。
- 子代理是一次咨询，而不是一条流：你看到的是结果，不是中间的往复。
- 架构师依据提示词和项目文件重建这个角色；回答质量 = 提示词质量 + 方法论文件的
  完整度。
- 设计师以 web 思考；转译到目标技术栈是主导会话的一步。
