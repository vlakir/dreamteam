# Backlog (dreamteam package)

Парковка идей и задач **разработки самого `dreamteam`-пакета**
(scaffolding CLI на Copier). В derived projects (создаваемых через
`dreamteam init`) — свой собственный `BACKLOG.md` с другим
содержимым; они не пересекаются, потому что репо `dreamteam`
содержит template как **package data** в `src/dreamteam/template/`,
не как файлы в корне.

Структура и правила: порядок имеет значение (сверху — что
планируется ближайшим), формат —
`- **T<NNN>** — [<дата>] <описание>`. Когда задача берётся в работу
— переезжает в `BOARD.md → To Do`.

**Scope правила нумерации:** `max()` для T-ID считается по
`BACKLOG.md`, `BOARD.md` и `CHANGELOG.md` этого репо. Раньше
(до v1.0.0) файлы имели префикс `TEMPLATE-`; ADR об обратном
ренейме — в `DECISIONS.md`.

- **T031** — [2026-07-19] Встроить в шаблон **дисциплину тяжёлых
  тест-прогонов при параллельных worktree**: мьютекс-обёртка + правило
  «не стекать прогоны» + опция лёгкого дефолтного прогона (coverage
  отдельно).

  **Контекст.** Отработано на живом проекте (`calque`, задачи T168/T169).
  Несколько worktree делят одну машину; полный `pytest` держит сотни МБ–
  ~1 ГиБ RSS, и два-три прогона одновременно (рядом с тяжёлой IDE)
  стекаются в **OOM/зависание** — ловили на реальной 16-ГБ машине.
  Это прямое продолжение [[T030]] (параллельные worktree) и его пункта
  «общие dev-сервисы — один экземпляр на пользователя»: общий ресурс тут —
  оперативная память. Стоит зашить в шаблон, чтобы derived-проекты
  получали дисциплину «из коробки».

  **Что зашить в template (`src/dreamteam/template/…`: скрипт +
  генерируемый проектный `CLAUDE.md`), самодостаточно:**
  - **Мьютекс-обёртка тяжёлого прогона** (в calque — `scripts/pytest-guard.sh`):
    drop-in замена `<runner> pytest`, сериализующая тяжёлые прогоны между
    ВСЕМИ worktree через **общий per-user lock** (в calque — `flock` на
    `${TMPDIR:-/tmp}/<proj>-pytest-<uid>.lock`). Concurrency 1, поведение
    при занятом локе — **блокирующее ожидание** (второй прогон ждёт
    очереди и стартует сам; удобнее «фейлить сразу»). Незакоммиченное
    состояние сессий не трогается — сериализуется только запуск.
  - **Правило в проектном `CLAUDE.md`:** полный/coverage-прогон и pre-push
    тест-гейт — через обёртку, не голым раннером; особенно при живых
    параллельных сессиях. Точечный однофайловый прогон (лёгкий) — можно
    напрямую. CI гонит напрямую (изолированный раннер — делить нечего).
  - **Опция лёгкого дефолтного прогона:** держать coverage ВНЕ дефолтного
    `addopts` (трассировщик покрытия заметно раздувает RSS/CPU), а порог
    покрытия считать **явной командой** в pre-push-гейте и CI. Дефолтный
    `pytest` остаётся лёгким для повторяющейся локальной итерации. Порог
    (напр. ≥80% на `src/`) сохраняется — просто в явной команде, не в
    дефолте. Оформить как дефолт шаблона (с коротким пояснением-tradeoff).

  **Обобщения при переносе в шаблон (важно — НЕ тащить calque-специфику):**
  - **НЕ переносить** Qt/PySide-специфику из T168 (`gc.disable()` ради
    teardown-крашей Shiboken, декомпозиция «утёкшие Qt-циклы») — это про
    конкретный GUI-стек, не про шаблон.
  - Нейтральные термины; не завязываться на конкретный пакетный менеджер
    (говорить «раннер тестов проекта») и git-хостинг.
  - **Кроссплатформенность lock-механизма:** `flock` — util-linux
    (Linux/macOS-подобные). На Windows его нет — обёртка должна
    **деградировать корректно** (no-op-сериализация или иной механизм),
    а не падать. Проработать на clarify (возможно: bash-обёртка Linux/macOS
    + отдельная стратегия или явный no-op под Windows).

  **Триггер:** следующая версия пакета (вместе с [[T030]], одна тема
  параллельных worktree). Полный ритуал шаблонной правки; ADR, если меняем
  структуру генерируемых файлов (новый скрипт в template + правка
  генерируемого `CLAUDE.md`/`pyproject`).

  Acceptance (предварительно):
  - derived-проект после `dreamteam init` получает мьютекс-обёртку
    тяжёлого прогона и самодостаточный раздел в проектном `CLAUDE.md`
    (правило «не стекать тяжёлые прогоны», через обёртку);
  - дефолтный тест-прогон лёгкий (coverage вынесен), порог покрытия
    сохранён в явной pre-push-команде и CI;
  - обёртка корректно ведёт себя без `flock` (Windows) — не падает;
  - формулировки нейтральны, без Qt/`mem0`/хостинг-специфики.

- **T030** — [2026-07-12] Встроить в шаблон методику **параллельной
  работы в нескольких git worktree** + обобщить принцип «durable-знание
  о проекте живёт ВНУТРИ проекта».

  **Контекст.** Отработано на живом проекте (`calque`): несколько задач
  велись одновременно, каждая в своём `git worktree`, в разных папках
  параллельно работали несколько ассистент-сессий. Всплыли типовые
  грабли, которые стоит зашить в шаблон, чтобы derived-проекты получали
  их «из коробки», без пере-объяснения каждую сессию.

  **Что зашить в template (`src/dreamteam/template/…`, генерируемый
  проектный `CLAUDE.md`), самодостаточно — derived-проект может быть у
  другого пользователя, без «нашего» глобального `CLAUDE.md`:**
  - **Реестр — встроенный `git worktree list`** (общий `.git`; из любой
    папки-клона виден весь список path+ветка+HEAD). Самодельный
    файл-реестр не нужен и не заводится.
  - **Ритуал старта:** `git worktree list` + `git branch
    --show-current`; >1 worktree → рядом другая сессия, её ветка и файлы
    под её путём = off-limits.
  - **Изоляция:** одна ветка на worktree; гейты/тесты из СВОЕГО
    окружения (наследованный env виртуального окружения может указывать
    на чужой `.venv` — активировать своё); общие «дописываемые сверху»
    журналы (`DECISIONS/CHANGELOG/BOARD/BACKLOG`) конфликтуют при мерже
    параллельных задач → перед PR `fetch`+`rebase` на свежий main и
    разрулить (сохранить чужие записи, вписать свою). Код разных задач
    обычно сливается чисто.
  - **Жизненный цикл:** create (`git worktree add`) → перед PR
    rebase+squash в один коммит → merge → `prune` + удалить ветку.
  - **Уборка за собой СПРОСИВ разрешения:** закончил задачу/связную
    группу — предложить убрать папку-клон, но `git worktree remove`
    только после явного «да» пользователя (в клоне может быть нужное —
    недокоммиченное, заметки, артефакты). Не удалять молча.
  - **Общие dev-сервисы — один экземпляр на пользователя:** если запуск
    приложения поднимает общие БД/контейнеры/локальный конфиг, две
    параллельные копии их делят (расходящиеся миграции/состояние) —
    предупредить и показать, как изолировать (отдельная БД/конфиг).

  **Обобщённый принцип памяти (ГЛАВНОЕ, memory-agnostic).** Всё
  durable-знание о проекте живёт **ВНУТРИ проекта** — в его репо
  (`CLAUDE.md`, `DECISIONS.md`, `docs/`, `specs/`). Любой **внешний**
  слой персистентной памяти ассистента (mem0 или иной механизм, если он
  у пользователя вообще есть — может и не быть) — **только опциональный
  дубль/подстраховка**; методика обязана работать и БЕЗ него. Причина
  двойная: (1) внешняя память ассистента часто привязана к пути/машине
  и не переносится/не шарится между worktree и платформами; (2) знание
  о проекте должно уходить вместе с репо любому, кто его клонирует.
  Правило: сначала фиксируй факт в файлах проекта, потом (если механизм
  есть) опционально дублируй вовне — «хочешь дублируй, но всё о проекте
  внутри проекта».

  **Обобщения при переносе в шаблон:** нейтральные термины
  («Разработчик» / «пользователь», без персонального имени); не
  завязываться на конкретный memory-механизм (`mem0`) — говорить
  «внешняя персистентная память ассистента, если есть»; не завязываться
  на GitHub-специфику (worktree/rebase/squash — общий git; PR/MR — любой
  хостинг).

  **Триггер:** следующая версия пакета (планируется «загнать в прод»).
  Полный ритуал шаблонной правки; ADR, если меняем структуру
  генерируемых файлов.

  Acceptance (предварительно):
  - в генерируемом проектном `CLAUDE.md` есть самодостаточный раздел про
    параллельные worktree (реестр / ритуал / изоляция / цикл /
    уборка-с-запросом / общие dev-сервисы);
  - зафиксирован memory-agnostic принцип «durable-знание о проекте —
    внутри проекта; внешняя память — опциональный дубль, методика
    работает без неё»;
  - формулировки нейтральны (без персонального имени, без привязки к
    `mem0` и к конкретному git-хостингу);
  - derived-проект после `dreamteam init` получает это без ручной
    донастройки.

- **T024** — [2026-05-15] Self-review Claude'а опционален при
  наличии рабочего внешнего ревью-бота.

  **Контекст.** Текущая методика требует self-review Claude'а
  на **каждый** PR по 7-пунктовому чеклисту (scope /
  архитектура / код / линтеры / документация / соглашения /
  безопасность), а сторонние ревью (CodeRabbit) — «не
  игнорировать, обсуждать». На практике с CodeRabbit (T007,
  v1.5.0) бот покрывает ровно тот же круг вопросов
  (catches scope drift, security, style, конкретные баги),
  и self-review Claude'а — дублирование с confirmation bias
  (Claude ревьюит свои же изменения). Hybrid-стратегия из
  CHANGELOG `[1.5.0]` (CodeRabbit baseline + manual Claude
  для нетривиальных PR) уже эту проблему фиксировала
  поведенчески, но формальное правило в `CLAUDE.md` не
  обновлялось.

  **Новое правило (предлагаемая формулировка):**

  - **Дефолт при подключённом боте.** Если в проекте
    подключён рабочий автоматический ревью-сервис
    (CodeRabbit, qodo-code-review, или аналог), который
    ревьюит каждый PR — self-review Claude'а **не
    требуется** по умолчанию. Бот = baseline review.
  - **Targeted Claude-review** — опционально, по запросу
    Разработчика или собственной инициативе Claude, если
    PR нетривиален (архитектурное изменение, security-
    sensitive code, сложный scope). Не формальный 7-
    пунктовый pass, а deep review по конкретной зоне риска.
  - **Исключение — methodology / docs PR.** Бот заточен
    под код; PR с правками только markdown / методики
    (`*.md`, `specs/**`, `docs/**`, ветки `meta/*` /
    `rules/*`) бот ревьюит слабо. Здесь self-review
    Claude'а остаётся **дефолтом** (по тому же 7-пунктовому
    чеклисту, адаптированному под доку: scope / коherence /
    cross-refs / typos / methodology consistency).
  - **Fallback при недоступности бота** (rate-limit,
    monthly quota исчерпана, сервис лёг). Если бот не
    прошёл по PR (например, CodeRabbit не отчитался в
    течение разумного окна) — Claude делает self-review,
    чтобы не оставлять PR без review. Memory
    `feedback_coderabbit_retrigger.md` про
    `@coderabbitai review` retrigger продолжает действовать.

  **Состав правки:**

  - `~/.claude/CLAUDE.md` — раздел «Code review каждого
    PR» (строки 240+) переписать: убрать «по умолчанию
    ревьюер — Claude», поставить условный flow с тремя
    ветками выше.
  - `~/.claude/projects/-home-vlakir-programming-dreamteam/memory/feedback_review_each_pr.md`
    — обновить под новое правило либо deprecate
